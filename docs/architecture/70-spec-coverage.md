# 70 — Spec Coverage Matrix

> **Traceability between the spec (`docs/spec/`) and the build (`backend/`).** Every black-box requirement, mapped to its implementation status, the code that realizes it, and the decision behind it. This is the "what's done vs. next" view for planning — kept current as slices land. The spec is the contract; this is the ledger against it.
>
> Status is judged against *backend* behavior. Frontend-only requirements (in-browser runners, rendering) are marked as such. When a status is anything but ✅, the **Notes** say what remains.

## How to read this

| Mark | Meaning |
|---|---|
| ✅ | **Built & tested** — implemented in `backend/`, with tests. |
| 🟢 | **Active slice** — being built right now (the current working set). |
| 🟡 | **Partial** — the foundation is in; a named piece remains. |
| 🔭 | **Deferred by decision** — design is settled (a D-number), build is deliberately held until its feature/seam is in scope. The seam is reserved; this is *not* an oversight. |
| ⬜ | **Pending** — capability/feature not yet started. |

**Rollup (≈153 requirements).** Every **feature surface** in the spec now exists and is wired end to end — no screen renders mock data, and no MUST-level *feature* is missing. What remains is refinement (SHOULD/MAY), two rows deferred by decision, and **one genuine MUST-level gap: `AE-2`'s tool-category list** (below).

The foundation was already in: the agent engine, run substrate, event protocol, approval, memory, auth, at-rest encryption, the model registry, the code-execution sandbox, the View (versions + live head), the attention surface, deep research, and skills. The last sprint closed the remaining surfaces on top of it — **mail** (`EMAIL-*`: IMAP/SMTP, JMAP and provider APIs behind one transport seam, with AI triage, learned reply style, and every fetched body fenced as untrusted), **calendar** (`CAL-*`: recurrence, ICS, CalDAV, natural-language entry), **external tools** (`MCP-*`/`INTEG-*`: registered servers and configured connectors under one per-tool trust policy), the **secrets manager** and **encrypted backup** (`VAULT-*`/`BACKUP-*`, each under its own KDF), **AI document editing** (`DOC-3`: anchored suggestions the operator accepts or rejects), **scoped API tokens** (`AUTH-4`), and two hardening rows — operator tool disablement (`AE-3.3`) and sealed conversation titles (`XC-SEC-3`).

**The one MUST still open.** `AE-2` lists the tool categories the agent MUST be able to invoke, and several have no toolset: host filesystem read/write, inter-agent (sub-sessions, model-to-model, pipelines), model management, research-as-a-tool, and configuration. Each is a thin adapter over a capability that mostly already exists — this is a build queue, not a design problem — but it is a MUST, and calling it anything else would misreport the state.

**This ledger is not trustworthy on its own — audit it against the code.** Three rows were wrong in the direction that matters most: `MEM-3`, `AUTH-5` and `CMP-1..3` were all marked unbuilt while working, tested code existed. And the rollup that preceded this one claimed every MUST was built; checking the *spec* rather than the ledger found `AE-2` open and `CAL-1`'s edit path unbuilt (since fixed). A row here is a claim to verify, not a fact.

The pattern that held throughout: **the hard cross-cutting machinery was built once and inherited.** Every feature above reduced to a capability in `services/`, a thin tool in `tools/`, a route module, and a migration — none needed new infrastructure, and the one genuinely novel piece of design in the whole sprint was the mail transport seam, which itself copied an existing shape.

## Cross-cutting — Security (`XC-SEC-*`)

| Req | Status | Realized by | Notes |
|---|---|---|---|
| XC-SEC-1 auth before any feature; locked-until-unlocked | ✅ | `core/auth` ASGI gate, `core/vault` | Global gate; restart re-locks. **Two deliberate exemptions** (`core/auth.py`'s exempt prefixes) bypass **both** the auth check and the vault-lock check, each credentialed instead by an unguessable path token: `/previews/*`, so a sandboxed opaque-origin iframe loads a preview without the operator cookie, and `/tasks/hooks/*`, so an external trigger can fire a scheduled task — meaning `POST /tasks/hooks/{token}` starts a run with no session and a locked vault (the run's own lock-aware machinery parks its writes until unlock). Documented, not accidental. |
| XC-SEC-2 single operator, approval-gated | ✅ | D14 throughout | No tiers; sensitivity, not privilege. |
| XC-SEC-3 all data AES-256 at rest; password one-way hashed | ✅ | `core/crypto` (AES-256-GCM), `core/vault` (Argon2id verifier); `services/sealing.py` for a column converted after the fact | App-layer per-column AEAD (D17). The two remaining cleartext user-content columns are now sealed (`5a07sec0007`): `Conversation.title` — an LLM summary of the operator's own first message, the most revealing single line per thread — and `CorpusSource.path`. A migration can't encrypt existing rows (the schema upgrade runs at startup, before any login, with no key in memory), so the shape is: the migration adds the sealed column, a lock-aware backfill in `app.py` seals the legacy plaintext after unlock and nulls it, and every read prefers the ciphertext with a cleartext fallback — a half-migrated DB reads correctly from the first request. |
| XC-SEC-4 password derives the at-rest key (login == unlock) | ✅ | `core/vault` (Argon2id KDF → memory-only DEK) | One event, no separate credential store. |
| XC-SEC-5 untrusted external content marked as data | ✅ | `core/untrusted.py` (`wrap_untrusted` + `untrusted_preamble`/`untrusted_fence`); applied in `services/webfetch` to fetched pages, `services/search` to search snippets, `tools/corpus.py` to every corpus hit (folders/documents/uploads), `agent/attachments.py` to chat-attached file text (both the attach turn and replayed history), `tools/mail.py` to every subject/sender/snippet/summary/body, and `tools/external.py` to every external tool result; `ReinjectSystemPrompt` installed unconditionally on every agent turn (`agent/engine.py`) | **Complete.** Mail was the last unwrapped ingress and is the sharpest case — an attacker chooses the words and they land in the model's context — so nothing read from a mailbox reaches the model unfenced, with a per-call nonce the content can't predict so a message can't forge its own closing marker to break out. External tool results are wrapped on the same grounds. |
| XC-SEC-6 every record owner-stamped | ✅ | `owner_id` on every top-level `models/` entity; child rows reach their owner by FK | Multi-user enforcement deferred (one human). **Not literally every entity carries the column**: `Message` (`models/conversation.py`) and `TaskRun` (`models/task.py`) have no `owner_id` — each is a child row whose owner is reachable only by joining its parent (`conversation_id` / `task_id`), and both are cascade-scoped to that parent. Deliberate (one owner per aggregate, no denormalized copy to drift), but it means a future multi-user ownership check on those two tables is a join, not a column read. |
| XC-SEC-7 agent code exec isolated from host; disabled if no sandbox | ✅ | `services/sandbox`, `tools/code.py` | Container backend; fail-closed (no runtime ⇒ capability absent), never host fallback (D23). Per-conversation live session, idle-reaped, vault-sealed workspace. |

One `view.snapshot` event per version (carrying its preview descriptor); the frontend renders one viewport — the head/preview on stage plus a version timeline to compare. Not a named spec feature; it is the agent's render surface for sandboxed output and a building block toward `DOC-*`/`RUN-1`-class display. Distinct from `RUN-1` (which is an in-browser, host-free snippet runner — still ⬜).

| INTEG-1…3 third-party integrations | ✅ | `models/external_tool` (`Integration`), `services/integrations` (static preset catalog + `IntegrationService`), `routes/integrations` (`/integrations*`), `tools/external` (one tool per action), `features/integrations` (the INTEGRATIONS screen) | Connectors are instantiated from a preset catalog (GitHub, GitLab, Jira, Slack, Notion, ntfy) with the credential vault-sealed and never returned, and `POST /{id}/test` proves it before anything relies on it. Calling an action is built: the preset fixes the request's shape, path parameters are percent-encoded, the resolved URL must stay inside the operator's base URL, redirects are refused rather than followed (they'd carry the credential), and every outbound URL is SSRF-guarded — which is why the presets are public-cloud services. Each action is exposed to the agent as its own tool — so it is separately describable and separately trustable, where one generic "call this connector" tool would collapse read and write into a single trust decision — and every response is wrapped as untrusted third-party content before it reaches the model. |

> **Supporting infra, not a spec feature:** the **model role→endpoint registry** (`services/registry`, `models/registry`, `/models/*`) is the single source of truth for model resolution — named roles (`main`/`utility`/`embedding`) → ordered `FallbackModel` chains, per-conversation `main` override (a provider **and** a model on it), API keys encrypted at rest. An **endpoint is one connection to a model API**, typed by a `provider` id that dispatches to an adapter in `services/providers` (D36): `openai-compatible` is the universal path, **Anthropic and Google are spoken natively** (Pydantic AI `AnthropicModel`/`GoogleModel` — no compat shim), and `local` marks a serving-managed engine whose `live_status` is process liveness distinct from the operator's `enabled` switch. Its served models are **discovered at runtime** through the provider's own models API (`GET /models/endpoints/{id}/models`), so the chat model is chosen from a top-bar picker rather than baked per endpoint; `GET /models/providers` serves each adapter's preset (default base URL, key hint, capability defaults) so the frontend prefills instead of hardcoding. It realizes **D16** and directly backs `AE-5.3`, `CHAT-4`, and `EMB-*`. Two operator-facing surfaces ride this registry: **guided setup** (Cookbook → *Get Started*: pick a provider preset → paste a key → *Connect & use this* tests the endpoint and auto-selects a working model, so chat works without the operator choosing one) and **endpoint health & recovery** (per-endpoint connection test with backend-categorized errors, disable-without-delete). Both are UX over existing infra — no dedicated spec rows yet (candidate `COOK`/`XC` additions to surface).

## What this says about "next"

**The feature surfaces are done; the agent's reach into them is not.** Every capability in the spec now exists behind a REST surface an operator can use — mail, calendar, external tools, the secrets vault, backup, documents, scheduling, research, serving, skills. The gap that remains is `AE-2`: several of those capabilities have no *tool*, so the agent can't drive what the operator can. That is the natural next queue, and it is small work per item — a host-filesystem tool (approval-gated), an agent-facing model serve/stop tool, a research-start tool, a configuration tool, and the inter-agent set.

**Everything else left is refinement.** Whole-turn history summarization (`CHAT-4`/`AE-5.4` — deterministic tool-result compaction is in; the utility-model pass over older turns is not), `TASK-3`/`TASK-4`, document dedup/export/labels, PDF form fields, report archiving, and the skill benchmark/publish MAYs. Two rows stay deferred by decision: `AUTH-3` (user administration — there is one operator; the `owner_id` seam carries it forward) and `AE-6.4`.

**The sprint that closed these surfaces validated the architecture more than it changed it.** Seven features were built in parallel worktrees against a frozen shared-file reservation, and every merge conflict was mechanical — each track had narrowed its own reserved line, none had collided on logic. That is only possible because the seams were real: a feature is a capability in `services/`, a thin tool in `tools/`, a route module, and a migration. Skills demonstrated it first (`SKILL-1..3` / D32 — a format layer, a store, a route, a three-tool toolset, and no new infrastructure at all); mail, the largest feature in the app, needed exactly one new idea, and copied its shape from the serving adapters.

This is additive over the foundation, not a rebuild — which is the whole point of having spent the early passes on the chassis.
