# Architecture Decisions — open register

Decisions with genuine trade-offs. Each is **OPEN** until you weigh in; recommendations are starting points, not commitments. Referenced inline from the docs as **⟦OPEN: Dn⟧**.

Status legend: 🔵 open · 🟢 decided · ⚪ deferred (revisit when the area is built).

---

### D1 — Run streaming transport 🟢 DECIDED: SSE + POST control
**Question.** How does the server push the run event stream to the client?

- **SSE (server→client) + plain POST for control.** Native `Last-Event-ID` replay (matches `AE-7` "receive the output it missed" with zero custom catch-up logic); trivial to proxy; text-only is fine for our events. Cost: one-directional (control like *stop* is a separate POST — which we want anyway), and HTTP/1.1 per-origin connection caps (a non-issue over HTTP/2).
- **WebSocket (bidirectional).** One socket for stream + control; binary-capable. Cost: resume/catch-up is *manual* (we'd rebuild what SSE gives free), reconnection and proxying are fussier.
- **Both.** More surface to maintain for little gain at our scale.

**Decision:** **SSE + POST control.** It makes `AE-7` continuity nearly free, and we never need client→server streaming. Revisit only if a feature genuinely needs duplex.

---

### D2 — Concurrency / run-execution model 🟢 DECIDED: in-process asyncio
**Question.** Where do Runs actually execute?

- **In-process asyncio tasks + in-memory registry/broker.** Fits the single-operator, single-host profile. Model inference is an HTTP call to a local OpenAI-compatible server, so it never blocks the loop. `AE-7`'s "continuity need not survive a server restart" *explicitly licenses* in-memory state. Simplest possible thing that satisfies the spec.
- **External queue + worker (Redis/Celery/RQ).** Survives restarts, scales horizontally — neither of which the spec requires, and both add operational weight against the local-first principle.

**Decision:** **In-process.** A `RunRegistry` of asyncio tasks with a bounded global concurrency limit (Pydantic AI's own `ConcurrencyLimit` can cap concurrent agent runs; a small queue absorbs bursts — also satisfies `TASK-5` "no overlapping overload"). Keep the broker abstraction clean so an external backend is a later swap, not a rewrite.

**Parallelism (single host, many things at once).** The app runs as a **single main process** — required, because the Run registry, event broker, and resume buffers are **in-memory** (`AE-7`); multiple uvicorn workers would fragment that state and break continuity. We parallelize *within* the process: **asyncio** for massive I/O concurrency (concurrent Runs, parallel tool calls, concurrent search/read per `DR-3.4`, all background workers); a **ThreadPoolExecutor** for GIL-releasing native CPU work (crypto, SQLCipher, numpy/embeddings) — genuinely parallel; a **ProcessPoolExecutor** for heavy pure-Python CPU (parsing/extraction) for true multi-core. **Honest bottleneck:** concurrent *LLM* calls serialize on the model server's batching — one big local model won't run N turns truly in parallel; the separate role-endpoints (D16, e.g. `utility` on a smaller server) let tiers run concurrently without contending. We max out I/O + CPU parallelism; model throughput is bounded by what's served.

### D3 — Tool-relevance mechanism (`AE-4`) 🟢 DECIDED: no relevance layer — the model discerns
**Question.** How do we pick "only the tools relevant to this request" while always keeping a core set?

**Decision:** **Don't pre-filter at all.** Present the full (access-gated) catalog and let the model — a capable native-tool-calling model (`AE-8.1`) on one powerful host — discern what to invoke. `AE-4.1` is a *SHOULD-performance*, explicitly waivable with reason; the reason is our deployment profile, and the directive to not overcomplicate. We avoid the latency, infra, and misroute-failure modes of a selection layer entirely.

Consequences:
- The toolset stack drops its `.prepared(relevance_select)` step; only the **access gates** remain (privilege → enabled → naming).
- `AE-4.2` ("doc tools available when a document is open") is **trivially satisfied** — every tool is always present.
- The seam stays open: if the catalog ever grows large enough that the full tool list hurts accuracy or token cost, a `.prepared()` relevance step can be slotted in later **without touching anything else** in the stack. Candidate mechanisms if that day comes: embedding similarity (reuses our embedding capability) or a cheap classifier.

Rejected for now (kept for the record): embedding similarity · LLM classifier/router · static category routing · hybrid — all add cost/complexity the profile doesn't require.

**The honest nuance.** This is sound *provided the catalog stays lean*. Token cost and latency are neutralized by prompt-caching the (static) tool-definition prefix; the only real risk is **selection accuracy, which scales with total tool count** (capable models stay sharp to ~20–40 tools, degrade past ~50–80). The correct lever is therefore **tool design, not filtering**: coarse, action-parameterized tools (one `document` tool with an `action` field, not five) keep the catalog in the safe zone by construction. Viewed this way, `AE-4` is plausibly an **artifact** of the suboptimal original — a relevance index bolted on to cope with a sprawling, un-consolidated catalog. We avoid the cause instead of patching the symptom. **Watch item:** total tool count and observed selection accuracy on the actual local model; the `.prepared()` seam is insurance if a future catalog genuinely outgrows the model.

### D4 — Verifier / corrective meta-loop policy (`AE-5.2`, `AE-5.5`) 🟢 DECIDED: heuristic, configurable, capped
**Question.** After a turn, do we judge success and retry?

- **Always-on.** Highest reliability; every turn pays a judge round-trip and possibly a re-attempt.
- **Operator-configurable, default off (or on only for tool-producing turns).** The spec marks this SHOULD/MAY and says it MUST be bounded and MAY be operator-configurable — so config is sanctioned. Pay the cost only where it earns its keep.
- **Heuristic trigger.** Verify only when the turn produced a checkable artifact (a file, a document, a deliverable the user named).

**Recommendation:** **operator-configurable, default to the heuristic trigger**, with a hard cap on corrective attempts (e.g. 1). Judge model is the configurable "utility" model, separate from the main one. The no-progress **loop-breaker** (`AE-5.1`) is *always on* and independent of this — it inspects the running message history / tool-call signature and aborts on repetition.

### D5 — Chat-vs-agent routing (`CHAT-3`) 🟢 DECIDED: single always-agent path
**Question.** "Decide per message whether a direct answer suffices or tools are needed."

- **Single always-agent path.** Tools are always *offered* (relevance-narrowed), the model simply may call none. One code path; relevance selection naturally collapses to "core tools only" for chitchat. Slightly more prompt overhead on trivial messages.
- **Pre-classifier fast path.** A cheap check routes trivial messages to a tool-less, cheaper config. Lower latency/cost on small talk; a second path to maintain and a misroute risk.

**Recommendation:** **single always-agent path** to start (simplest, no misroute failure mode); the relevance scorer (D3) already does the practical work of not burdening trivial turns with the full catalog. Add a fast-path later if latency data justifies it.

### D6 — Context reduction near the limit (`AE-5.4`, `CHAT-4`) 🟢 DECIDED · ✅ BUILT
**Question.** How do we stay within the model's context window?

- **Pydantic AI history processor** that trims oldest turns when token budget is tight — cheapest, lossy.
- **Summarize-and-replace** older turns via the configurable utility model — preserves the thread, costs a call.
- **Hybrid:** keep a pinned head (system + active task + open document, which `AE-5.4` says MUST survive) + summarize the middle + keep recent verbatim.

**Recommendation (defer):** implement as a history processor so the mechanism is swappable; start with **hybrid** (pin the active task + open doc, summarize the middle with the utility model). Revisit when we measure real conversations.

**Built (first slice — tool-result compaction, `agent/compaction.py`), with three refinements the build settled:**
- **The seam is a `ProcessHistory` capability, and it is *not* persistence-transparent** — a history processor's output *becomes* `result.all_messages()`, which the engine persists. So "compact freely, persist the original" does **not** work. The build instead leans on the fact that the engine only persists `messages[start:]` (the current turn): the processor compacts **only prior-turn** tool results and never the current turn. Crucially the prior/current boundary is the **persistence index** (`start`), threaded in explicitly as `CompactionContext.protect_from` — *not* inferred from the last `UserPromptPart`. The verifier's corrective re-attempt injects a second user prompt mid-turn, so a last-prompt heuristic would push the original attempt's tool outputs onto the "prior" side and persist them as unrecoverable digests; anchoring to `start` keeps the protected set and the persisted set identical. The operator therefore keeps every tool output in full (persisted + streamed); only the model's replayed view of *prior* turns is condensed, re-derived from the full DB history each turn. (See `tests/test_compaction.py`.)
- **Trigger is a fixed rolling window, not token pressure.** Keep the K most-recent **prior-turn** tool results full (current-turn results are protected wholesale and never consume the window); digest older oversized ones (over a size floor), one rolling off at a time. A pressure/"near the limit" trigger recompacts a bulk of history *between two adjacent steps*, which can yank an output the model is mid-reasoning over; a fixed window rolls smoothly and deterministically. The replacement is a **notice only** — the omitted size plus the `builtin_expand_tool_result` call that recovers the full output verbatim, no excerpt. String and JSON-shaped results are both eligible (binary/multimodal stays verbatim); the expand tool's own output re-condenses once it ages past the window, so repeated expansion can't grow history without bound.
- **No overflow guard — compaction is efficiency, never a safety net.** It never shrinks the window or drops content to force-fit. If context still overflows, the run **stops with a `limit="context"` notice naming the model's window** (operator starts a new chat / trims) rather than degrade into bad answers. Provider context-length errors are mapped into that same clean stop.

**Built (second slice — conversation compaction, `agent/summarize.py`), completing the hybrid:**
- **A pressure trigger *is* right here, because it fires between turns.** The first slice rejected "near the limit" for the tool-result window on the grounds that it recompacts a bulk of history *between two adjacent steps* and can yank an output the model is mid-reasoning over. That objection is specific to compaction firing **inside** a turn's tool loop. Whole-turn folding runs in the orchestrator **prelude**, before the agent starts, so there is no in-flight reasoning to disturb — which is exactly why the deferred half can use the trigger the built half could not. Threshold is a fraction of the model's declared context window (default 0.95), operator-tunable globally and per conversation; an endpoint that declares no window never fires (there is nothing to measure against, and folding on a guess would compact a thread that was never under pressure). Where usage is unreported — local servers commonly return `input_tokens=0` — a coarse chars/4 estimate over **text parts only** stands in; counting a retained inline image's base64 would read one screenshot as hundreds of thousands of phantom tokens.
- **Append a checkpoint; never rewrite the tree.** The summary is one new node at the tip carrying the id of the last node it covers. Nothing is deleted: the operator's transcript keeps every folded turn, and a rewind above the checkpoint restores the full replay for free. The two consumers reorder it in *opposite* directions, deliberately — the model gets it **hoisted to the front** as a preamble (`model_history`), the operator sees it **in chronological position** (`messages_view`), because to the model it is a premise and to the operator it is an event. Splicing it in at the boundary instead would mean re-parenting a live node and pulling the turns below it out of their own version sets.
- **The boundary is a turn start, and not every user prompt is one.** Folding stops at the *N*-th-from-last turn start after any earlier checkpoint (so a compaction can never reach back past one and re-expose its summary), which keeps the retained tail replayable — a turn always opens with an operator prompt, so the split can't strand an assistant tool call from its result, and `AE-5.4`'s "the active request MUST remain intact" holds by construction. A mid-run steering message persists as its own request, so counting bare `UserPromptPart`s would keep two asides verbatim and fold a real exchange; a turn start is a user prompt that is the root or directly follows a response.
- **`start` must be measured after every history rewrite — including the library's own.** The persistence index is `len(the list handed to message_history)`, and Pydantic AI returns `all_messages()` **shorter** than what went in: preparing the wire format merges consecutive requests (most chat APIs cannot carry two user messages in a row). Hoisting a summary in front of a tail that opens on a user prompt creates exactly that adjacency, and the un-normalized index silently dropped the operator's own message from the turn it persisted. The engine now normalizes consecutive requests up front (`_merge_consecutive_requests`) — which also fixes the same latent shift for `_split_injected_requests`' output replayed on the following turn.
- **Still not a safety net.** Unchanged from the first slice: a prompt that overruns the window anyway stops the run with the `limit="context"` notice. Compaction lowers pressure; it never force-fits. A summarizer outage degrades to "no compaction" and the turn proceeds on the full history.

**Revised — the first slice is withdrawn; the second is the whole answer.** The hybrid turned out to have one half too many. `AE-5.4` is a *conditional* requirement — reduce older context **when the conversation approaches the model's context limit** — and only the second slice's trigger reads that condition. Everything else shrank content on turns under no pressure at all, which is not what the requirement asks for and is worse than not reducing: it costs the model the middle of exactly the output it just requested. Removed:

- **Tool-result compaction** (`agent/compaction.py` + `builtin_expand_tool_result`). Its "fixed rolling window, not token pressure" argument was sound about *where* it fired but wrong about *whether* it should fire: a smooth deterministic roll is still a roll that happens when nothing is full. A large tool result now rides into context whole, and the `limit="context"` stop — always the real backstop — catches a pathological turn while saying so out loud.
- **The attachment inline-text cap** — replaced rather than deleted. An uploaded document is now staged into the conversation's sandbox and handed to the model **as a file with a path**; the model chooses what to read and pages through it itself. A 300-page PDF costs the marker's handful of tokens instead of a truncated prefix, which is strictly better than either the cap or no cap. The fail-closed sandbox means staging can fail, so that path degrades to the extracted text inline *in full*, and the marker says so rather than naming a path that isn't there.
- **`code_execute`'s stdout/stderr trim.** Same reasoning as the tool-result window.

Two consequences worth stating. `auto_compact_keep_turns` drops to **0**: with the summary standing in for the whole replay, a retained tail restates what the summary already covers at the exact moment there is no room for it — and `AE-5.4`'s "active request MUST remain intact" still holds, since the fold runs in the prelude over history the new prompt is appended after, and `compaction_plan` refuses to graft onto a branch point (a regenerate's leaf has children, so the request being re-answered is unreachable). And the fold is now **visible**: the `conversation.compacted` event and the cold-read divider both carry `messages_compacted` plus a before/after token estimate, computed the same way on both paths so a reload can't disagree with what the operator just watched happen.

### D7 — Schema migration strategy (`XC-DATA-2`) 🟢 DECIDED: Alembic from day one
**Question.** How does an existing install upgrade its schema on startup with no manual step?

- **Inline idempotent migration functions** run from DB init. Dead simple, zero deps, total control; you hand-write each change. Fine for a single-DB, single-operator app.
- **Alembic.** Industry-standard, autogenerate + downgrade, version table. Heavier; more ceremony than a local-first single-user DB usually warrants.

**Decision:** **Alembic from day one.** Versioned migrations with autogenerate + downgrade; the upgrade is **auto-invoked on startup** so `XC-DATA-2` ("applied automatically… upgrades in place," no manual step) still holds. Chosen over inline because schema churn is expected and **SQLCipher complicates in-place `ALTER`s** (some need table-rebuild/copy dances) — better handled by explicit, reviewable migration scripts than ad-hoc introspection guards.

**As built.** Alembic lives at `backend/migrations/` with the initial revision capturing the current schema (conversations, messages, model_endpoints, model_roles). `core.db.init_db` runs `command.upgrade(cfg, "head")` on every boot, handing Alembic the **live engine** via `config.attributes['connection']` rather than letting `env.py` build its own — this is what lets the in-memory test DBs (schema on one shared connection) migrate at all. `render_as_batch=True` is on so SQLite `ALTER`s use the table-rebuild dance (anticipating the SQLCipher note in D17). The CLI path (`alembic revision --autogenerate`, `alembic check`) builds its own engine from `sqlalchemy.url` / `ODYSSEUS_DB_URL`. The Mako template imports `sqlmodel` so autogenerated `sqlmodel.sql.sqltypes` references resolve.

### D8 — Conversation-history persistence 🟢 DECIDED: in-memory working set + write-behind queue
**Question.** What is the source of truth for a conversation, and how does it reach the DB?

**Decision:** **Write-behind hybrid.** While a user is engaged, Pydantic AI's in-memory `ModelMessage` history is the **live working set** (a pseudo-cache) — runs read/continue from it with zero DB round-trips on the hot path. As each message completes, it is **copied onto a persistence queue** that drains to the DB asynchronously, off the critical path. The DB is the **durable** record (survives restart, serves history/search/metrics); memory is the **fast** record (serves the active turn).

Mechanics:
- Persistence is a **queue consumer on the run substrate** — the same place run events flow. Message-completion enqueues a write job; a background drainer batches them to the DB. Backpressure-bounded; failures retry without stalling the run.
- The durable form is the serialized `ModelMessage` (via `ModelMessagesTypeAdapter`/`to_jsonable_python`) for **resume fidelity**, alongside a thin derived projection (role, text, timestamps, run id, token counts) for **listing/search/metrics**. The projection is derived, never authoritative.
- On resuming a cold session, the blob rehydrates the in-memory working set; from there it's memory-speed again.

This is the concrete instance of "we own the queues": the write-behind drainer is one of a small family of background workers (persistence, scheduling, notifications) on the in-process substrate.

### D9 — Auth credential transport 🟢 DECIDED: dual (httpOnly cookie + bearer)
**Question.** Bearer token vs cookie session.

- **Bearer token** in `Authorization`. Works identically same-origin or split-origin; aligns with `AUTH-4` scoped API tokens (same verification path for humans and programmatic callers). No CSRF surface.
- **Cookie session.** Smoother for a pure same-origin browser app; CSRF + `SameSite` to manage; awkward across origins.

**Decision:** **Dual.** Browser sessions use an **httpOnly, `SameSite` cookie** (not XSS-exfiltratable — important for an admin console holding shell/vault); programmatic/API clients (`AUTH-4`) use **bearer tokens**. The server accepts either credential on a request. Cost: standard CSRF protection on the cookie path (SameSite + CSRF token).

### D10 — Repo package granularity 🟢 DECIDED: fine split
**Question.** How finely to split the backend.

- **Fine split** (`runs/ agent/ tools/ services/ research/ routes/ models/ core/`). Each concern is findable; matches the layer map; more top-level packages.
- **Fewer packages** (e.g. one `src/` with sub-modules). Less navigation, but the agent engine is the heart of this project and benefits from breathing room.

**Recommendation:** **fine split.** The Run substrate, the engine, the tools, and the capabilities are genuinely different concerns with different change-rates; keeping them as siblings makes the dependency direction visible and enforces "tools are thin."

### D11 — Untrusted-content marking technique (`XC-SEC-5`) 🟢 DECIDED (technique deferred)
**Question.** How to mark web pages, emails, uploads, retrieved docs, and the open editor doc as *data, not instructions*.

- **Delimiter/sentinel wrapping** in the prompt text (clear, model-agnostic, slightly hacky).
- **Distinct structured content parts** (cleaner; depends on model/part support).
- **A dedicated "untrusted context" section** with an explicit standing instruction to treat it as data.

**Decision (technique deferred):** the marking is **ours** — Pydantic AI has **no built-in "treat-as-data" primitive** (confirmed: it offers only adjacent pieces — `ReinjectSystemPrompt(replace_existing=True)` to keep our system prompt authoritative over untrusted history, a **Hooks** capability to intercept tool/model calls, and `PrepareTools` for tool filtering). So `XC-SEC-5` is met by a single `wrap_untrusted()` helper used by every context-builder and content-returning tool — sentinel-delimited blocks + a standing "treat as data" instruction to start, upgrading to structured parts where supported. We **compose** it with `ReinjectSystemPrompt` (defend against poisoned history) and optionally a **Hook** running an injection classifier over tool outputs / retrieved content. Centralized = one place to harden.

### D12 — ORM choice 🟢 DECIDED: SQLModel, sync DB in threadpool
- **SQLAlchemy (async)** — most capable, most ubiquitous, verbose.
- **SQLModel** — Pydantic-native (pairs with FastAPI + Pydantic AI), thinner, younger.
- **Tortoise / others** — Django-like; less synergy here.

**Decision:** **SQLModel**, with the **DB layer run synchronously in a threadpool executor.** D17's SQLCipher driver is a *sync* DBAPI, so a fully-async ORM stack doesn't pair cleanly; blocking SQLCipher calls go in a threadpool to keep the event loop free while retaining SQLModel's Pydantic-native ergonomics. Drop to raw SQLAlchemy Core only where SQLModel is too thin. (SQLCipher releases the GIL during I/O, so threadpool DB calls genuinely parallelize — ties into D2.)

### D13 — Scheduling / event triggers (`TASK-*`) 🟢 DECIDED: in-process, lock-aware
**Question.** What drives recurring/cron/event/webhook tasks?

- **In-process async scheduler** (a tick loop or APScheduler) firing tasks as Runs. Fits the in-process model (D2); dies with the process (tasks reschedule on boot from the DB).
- **External scheduler.** Survives restarts independently; more moving parts against local-first.

**Decision:** **in-process scheduler** that materializes due tasks as Runs on the same substrate, with the schedule persisted so boot rehydrates it. Inbound webhooks (`AUTH-5`) are just authenticated endpoints that enqueue a Run.

**As built — `SchedulerService` (`services/scheduler.py`) + `models/task.py` + `routes/tasks.py`.** One asyncio task per process: sleeps until the earliest enabled task's `next_run_at`, wakes, fires whatever is due, sleeps again (`_wait_for`/`wake()` — any task create/update/delete re-arms the sleep rather than waiting out a stale timer). **Lock-aware** like `core.worker.WriteBehindWorker`: task `title`/`prompt` are vault-sealed, so the loop parks (`_wait_unlocked`) whenever the vault is locked and resumes on unlock, rather than erroring or busy-looping against unreadable rows. **At-most-one missed-fire catch-up:** a locked/parked scheduler (or a slow boot) can leave `next_run_at` sitting in the past; the loop's ordinary due-check already doubles as the catch-up path — an overdue task fires once and its next occurrence is recomputed anchored on *now* (not the stale timestamp), so a gap never floods a burst of backlogged fires. **Non-overlap (`TASK-5`):** each task's in-flight execution is tracked as an asyncio task in `_running`; a tick that finds the previous execution still live records a `TaskRun` with outcome `skipped` instead of double-running, and nudges that task's own schedule forward by a short poll floor (not its real cadence) so a busy task isn't re-detected-and-re-skipped every iteration. `fire_now` (the manual `run_now` route and the inbound webhook) funnels through the same `_dispatch` non-overlap path as the tick loop, so an on-demand fire and a real due-tick can never double-run the same task. An **agent** task executes as an ordinary Run in a fresh conversation, titled from the task, reusing the chat turn's own composition (`routes/chat.py`'s `resolve_turn_models`/`compose_turn`) rather than a second orchestration path; a **reminder** task fires its prompt verbatim as a notification, no AI phrasing (`TASK-6`). Inbound webhooks are realized as a per-task unguessable `webhook_token` (`secrets.token_urlsafe(32)`, the same construction as the previews proxy token) compared for equality on an auth-exempt route (`POST /tasks/hooks/{token}`) — the token *is* the credential, rotatable on demand via `PATCH /tasks/{id}` (`rotateWebhookToken`) — rather than a signed-payload/authenticated-endpoint scheme. **Deferred beyond this:** event triggers other than the inbound webhook, predefined automation actions/chaining (`TASK-3`), NL→schedule parsing (`TASK-4`), and email/push notification channels (`TASK-6` stays in-app only — see D30).

## Newly identified — not yet scheduled

Surfaced while surveying the whole spec; captured here so they aren't lost. One-liners now; each gets a full angle write-up when we pick it up. Ordered roughly by how foundational it is.

- **D14 — User model 🟢 DECIDED: single-operator, ownership seam only (C1) + capability gating by approval.** The spec's "privilege" conflates three independent axes; we separate them:
  - **Axis A — Authentication.** Kept fully — the app is a networked admin console and must authenticate even for one person (`XC-SEC-1`, `AUTH-1/2/4`).
  - **Axis B — Capability sensitivity.** *Reframed* from the spec's user-centric "admin-only tools" (vacuous with one admin) to **capability-centric**: certain tools are *sensitive* (shell, Python, filesystem-write, email-send, vault, config) and a sensitive call **requires explicit user approval before it executes** (see **D20**). This is what actually constrains the *autonomous agent*, which is the real threat surface here — not other humans.
  - **Axis C — Multi-tenancy.** **C1 (seam only):** every record carries an `owner_id` defaulting to the single operator, but **no ownership-enforcement checks and no per-user privilege/management UI are built yet.** Rationale: the one expensive, regret-prone future migration is retrofitting an owner column onto a populated schema and finding every query site — so we *pre-pay* that with a free column now and defer the enforcement (and `AUTH-3` user management, per-user setting overrides) until a second human actually exists. C0 (no column) saves a triviality at the price of that retrofit; C2 (full enforcement now) builds a multi-tenant fortress for a population of one, mostly unexercisable.

  Net posture: **authenticate fully · gate sensitive capabilities by approval · attribute data to an owner but don't enforce isolation yet.** Spec edited in place to match (`AE-3`, `XC-SEC-2/6`), keeping the spec black-box (no mention of the approval *mechanism*).

- **D15 — The concrete event protocol (`AE-6`) 🟢 DECIDED (v1 frozen).** The backend↔frontend streaming contract.
  - **Framing.** SSE; each frame's `id:` = a **per-run monotonic `seq`**, `data:` = a typed JSON envelope `{type, seq, ts, …payload}`. **One channel**, type lives in the JSON (not SSE's `event:` field) — simplest for our own client. Strict ordering by `seq` within a run; deltas are append-only.
  - **Resume (`AE-7`).** On reconnect the client sends `Last-Event-ID` = last `seq` seen; the server replays every buffered event with `seq >` that, then goes live. The per-run event buffer lives in memory for the run's lifetime.
  - **Versioning.** Protocol version announced in `run.started`; additive events/fields don't bump it, breaking changes do.
  - **Naming convention.** `entity.event`, **dot.lowercase**. Discrete (it *happened*) → past-tense verb (`started`, `committed`, `failed`); streaming increments → `delta`/`progress`.
  - **v1 event set:**
    - **Run:** `run.started` · `run.metrics` · `run.ended` · `run.error`
    - **Step:** `step.started` · `step.completed`
    - **Content:** `thinking.delta` · `answer.delta` (the `AE-6.3` reasoning/answer split)
    - **Tools:** `tool.started` · `tool.progress` (elapsed + partial, for slow tools) · `tool.completed` · `tool.failed`
    - **Documents:** `document.created` · `document.delta` · `document.committed` (`AE-6.2`)
    - **Notices:** `citation.added` · `approval.required` (D20) · `limit.notice`
  - **Deltas are coalesced server-side** (batched by time/punctuation, not one frame per token) for smoother render and lower frame overhead.
  - **Tool payloads are full inline** (complete args + results on the stream), not summaries — for user transparency; the client compacts them in an expandable view. (Full history is also persisted.)
  - These events are produced by translating Pydantic AI's native stream (`PartStartEvent`/`PartDeltaEvent` for thinking/answer parts, tool-call/return events, `FinalResultEvent`) and by emitting the ones the library doesn't know about (step boundaries, document lifecycle, citations, approvals, limit notices, run metrics, end).

- **D16 — Model/endpoint configuration & the utility model 🟢 DECIDED: named roles → endpoint/fallback-chain; single global utility.**
  - **Roles.** Fixed named roles the engine consumes: **`main`** (agent/chat), **`utility`** (cheap background work), **`embedding`** (recall), and later **`vision`** (scanned-PDF extraction). *(An `image-gen` role was listed here originally; image generation has since been struck from the spec — the product neither generates nor edits images.)* Each role binds to **an endpoint or an ordered fallback chain** of endpoints.
  - **`main` is overridable per conversation** (the chat model picker); all other roles are **global settings**.
  - **`utility` is a single global role** used by summarization (`CHAT-4`), verification (`AE-5.2`), email triage (`EMAIL-2`), NL parsing (`TASK-4`/`CAL-3`), titles, and memory extraction. **If unset it falls back to `main`.** Seam exists to split per-feature later, but we don't start there.
  - **Endpoints** are provider-agnostic: OpenAI-compatible `base_url` + model name + optional key + metadata — **context window** (feeds context reduction `AE-5.4`), and **capability flags** (native tool-calling is required `AE-8.1`; vision; thinking). Local (llama.cpp/Ollama/MLX/vLLM) or remote, per the local-first-but-configurable principle.
  - **Registry & resolution.** The endpoint registry lives in the **encrypted** settings, populated by manual config **and** the Cookbook (`COOK-4`) when it serves a model. At run start the orchestrator resolves the model from the role (with the per-session override for `main`) and builds the Pydantic AI model — wrapping the role's chain in **`FallbackModel`** (`AE-5.3`). The *"don't switch endpoints once answer text has streamed"* rule (`AE-5.3`) is enforced by **our** orchestrator, not the library: fallback is only allowed before the first `answer.delta`.
  - **Ripple → D18 / `EMB-2`:** the `embedding` role couples to the vector store; changing it must not lose existing recall, so each stored vector records which embedding model/dimension produced it (re-embed or segregate on change).
  - **As built.** The registry is the **single source of truth** for model resolution — there is no `.env` model seam and no runtime fallback to one (an unconfigured role is a degraded capability, surfaced as a clear "configure a model" error). It is realized as structured tables (`model_endpoints` + `model_roles`) rather than a generic encrypted-settings KV; only the **API key field is application-layer AEAD-encrypted** (the at-rest posture after whole-DB SQLCipher was ruled out — see D17), while base_url/model/flags stay indexable in the clear. The operator manages it through `/models/*`; the automatic-setup/Cookbook (`COOK-4`) populates it through the **same** `create_endpoint` + `set_role` write path. Roles resolve through `services.registry.ModelRegistry.resolve`; `services.llm` owns only the spec→model builders and the `FallbackModel` chain wrap.

- **D17 — At-rest encryption & key management (`XC-SEC-3`) 🟢 DECIDED.** All user data at rest is encrypted; the system is a vault that must be unlocked each boot.
  - **Cipher (settled by cryptography, not preference):** symmetric **AES-256-GCM** (or XChaCha20-Poly1305) *is* the post-quantum-safe choice — AES-256 retains ~128-bit strength under Grover; NIST excludes symmetric crypto from PQC transition. There is no PQ bulk cipher to adopt. PQC (hybrid X25519+ML-KEM) is reserved for *asymmetric key wrapping* (portable backups, future multi-device) — a deferred seam, not a dependency.
  - **Granularity — DECIDED: whole-DB + encrypted files.** SQLCipher encrypts the entire SQLite file (rows, indexes, FTS, embedded vectors — transparent to queries); large files (uploads/docs/gallery/personal-docs) are per-file AEAD blobs under the same key hierarchy. The vault keeps its own extra layer on top.
  - **As built — application-layer AEAD, not whole-DB SQLCipher (revised).** Whole-DB SQLCipher needs a SQLCipher-linked `sqlite3` driver, and there are **no portable wheels for our runtime (Python 3.14)** — adopting it would mean building from source / pinning Python, which breaks `XC-PORT-1` (must run with no OS-specific build dance across Linux/macOS/Windows). So at-rest encryption is **application-layer AES-256-GCM** under the *same* password-derived, memory-only DEK and key hierarchy described below — only the *granularity* changes: instead of the whole file being opaque, **each sensitive value is sealed in its column** (conversation message text + serialized `ModelMessage` blob; model-endpoint API keys), while structural metadata that must be indexed/ordered (ids, owner, timestamps, seq, kind, base_url, model name, capability flags) stays in the clear. Encryption happens on the **lock-aware** side of the write-behind queue, so a mid-turn lock parks the write rather than losing it. The cipher, key custody, lock lifecycle, and PQ posture are **unchanged** — only the boundary moves from "the file" to "the sensitive fields." **Trade-off accepted:** indexes/FTS over plaintext columns are not encrypted (acceptable — they hold structural keys, not content), and remembering to seal each new sensitive column is now a design responsibility (the model registry's `api_key` is the first to follow it). **The whole-DB design stays the target seam:** if portable SQLCipher wheels appear, or the data model grows enough that field-level coverage becomes error-prone, the `core.db` engine factory is the single swap-in point (Alembic already runs with `render_as_batch=True` for the `ALTER` constraints SQLCipher would impose). Large-file per-file AEAD (uploads/docs/gallery) is unaffected and lands with those features.
  - **Key custody — DECIDED: password-derived, lock-until-unlocked.** The operator's **login password is the key material**. Two-tier hierarchy: password → **KEK** via **Argon2id** (dedicated salt) → unwraps a random **DEK** (so a password change only re-wraps the DEK, never re-encrypts data). Auth-verifier and KEK are **domain-separated** (independent HKDF labels / salts) so the stored login hash is useless for decryption. The **DEK lives only in process memory** after unlock — never written to disk and never to any OS keystore (no Keychain / DPAPI / `libsecret` dependency), which also makes this the **most platform-agnostic** custody option: byte-for-byte identical behavior on Linux, macOS, and Windows. **Auth secrets stay hashed** (Argon2id), never encrypted (`XC-SEC-4`).
  - **Lock lifecycle:** on boot/restart the app is **locked** (encrypted data inaccessible); first successful login derives the KEK and unwraps the DEK into memory, **unlocking** it for the process lifetime. An explicit *lock* control (and optionally an idle timeout) wipes the DEK from memory, requiring re-unlock. Restart ⇒ re-unlock.
  - **Consequence — background work is lock-aware (ripple → D13).** The scheduler, email triage, reminder dispatch, webhook handlers, and the write-behind persistence drainer all touch encrypted data, so they **only run while unlocked**. While locked they **park gracefully** (persist intent, surface a "locked" status) rather than erroring or dropping events; on unlock they catch up a bounded backlog. After a restart, unattended features stay paused until the operator logs in — an accepted trade for maximum confidentiality.
  - **Consequence — app "locked" state surfaces to the client.** The shell needs a locked/unlocked indicator and an unlock prompt; health/connection status reflects it.
  - **Edge — `AUTH_ENABLED=false`.** At-rest encryption needs an unlock secret even when network auth is off. Resolution (provisional): the **unlock passphrase is conceptually separate from login** — disabling auth disables the *login gate*, not the *unlock*; the operator still supplies a passphrase to derive the key. (Equivalently, at-rest encryption makes an unlock step effectively mandatory.) Confirm when we build auth.
  - **Ripple → D18:** pushes the vector store toward **embedded (sqlite-vec inside the encrypted DB)** so embeddings are encrypted for free; an external Chroma would be a separate plaintext store needing its own encryption.
  - **Ripple → `BACKUP-*`:** a backup must be decryptable on another host, so export re-wraps the DEK under a **separate backup secret** (recovery key / passphrase) — the natural home for an optional PQ-hybrid (X25519+ML-KEM) key-wrap later. A forgotten password with no recovery key = unrecoverable data (accepted for a single operator; recovery key is the mitigation).

- **D18 — Vector store (`XC-DEG-1`, `MEM-2`, `RAG-2`, `EMB-*`) 🟢 DECIDED: pluggable interface, `sqlite-vec` default.** Vectors live in **`sqlite-vec` inside the encrypted DB** (D17) — one encrypted store, no extra service; brute-force KNN is fine at single-operator volumes. The pluggable interface keeps the seam to slot an external store (Chroma, etc.) if volume outgrows brute-force. Degrades to **keyword search** when vector search is unavailable (`XC-DEG-1`). Each vector records its embedding model/dimension so an `embedding`-role change (D16, `EMB-2`) re-embeds or segregates rather than corrupting recall.
  - **As built — brute-force hybrid in Python, *no* `sqlite-vec` (revised).** `sqlite-vec`'s whole justification was that whole-DB SQLCipher would encrypt its vectors "for free" (this entry's own phrasing). D17 moved to **app-layer per-column AEAD** (no portable SQLCipher wheels), and that premise is gone: `sqlite-vec` does KNN over **plaintext** vectors, which under per-column encryption would leave embeddings of private memories unencrypted at rest — and embeddings are invertible enough to leak their source text, contradicting `XC-SEC-3`. (FTS5 keyword indexing has the same plaintext-index problem.) So at single-operator volumes the store is **brute-force-in-Python over the decrypted working set**: vectors are AEAD-sealed in their column, and recall loads the owner's memories, decrypts, and scores each both ways — **dense** (cosine over embeddings, "by meaning") and **sparse** (token overlap, the keyword path) — fusing the two with **Reciprocal Rank Fusion**. This satisfies `MEM-2` (meaning + keyword fallback) in one pass, keeps every vector encrypted, needs **no native extension** (better for `XC-PORT-1`), and is microseconds at this scale. `EMB-2` is honored: dense comparison is gated to the same embedding model/dim, so a model change degrades to sparse rather than comparing across spaces. **The pluggable seam stands** — an ANN store (`sqlite-vec`/external) can slot back in when *volume*, not confidentiality, becomes the constraint, which is an explicit trade then (and would pair with whole-DB encryption if it returns). First realized for `MEM-*`; `RAG-*` reuses the same store.

- **D19 — Deep-research build approach (`DR-*`) 🟢 DECIDED: hybrid.** A **hand-coded outer pipeline** owns the deterministic concerns — rounds + time bounds (`DR-3.1`), source/query dedup (`DR-1.4`), per-round concurrency and source caps (`DR-3.4`), stop-when-comprehensive (`DR-3.2`), and the phase progress events (`DR-5.1`). Inside each round, a **Pydantic AI agent** handles the judgement-heavy step: analyze gathered evidence, refine the evolving answer, and identify remaining gaps to investigate next (`DR-1.2`). Both ride the **Run substrate** and reuse the **search + LLM capabilities** directly. This keeps the bounds explicit and testable while letting the model do the open-ended synthesis. Cost: two paradigms in one feature — kept clean by the pipeline owning control flow and the agent owning only the in-round reasoning.
  - **As built — `research/` (pipeline core) + `routes/research.py` (the product wiring).** The library/route split holds exactly as decided: `research/pipeline.py`'s `run_research` is pure — a plan and a question in, a report out, no routes/model-resolution/Run wiring — and everything that turns it into a product feature lives in `routes/research.py`, which builds an `Orchestrator` closure around it and submits that as an ordinary Run.
    - **Fan-out is dynamic, not a fixed per-phase agent count.** Within a round's `searching`/`reading` phases, the number of concurrent workers scales to that round's actual workload (fresh queries, hits worth reading) capped by `research_max_concurrency` — never a hardcoded N. A worker's own failure (a dead search provider, an unfetchable page) is swallowed inside that worker; it loses only its query/source, never the round (`DR-4.2`).
    - **Pre-run clarify/refine is plain REST, deliberately never a parked Run.** `POST /research/intake` and `POST /research/{id}/refine` are two small, one-shot Pydantic AI calls made directly from `routes/research.py` (a utility-model clarify judge, a main-model planner) — lightweight enough that parking them on the Run substrate would be needless ceremony. Only the frozen, operator-approved plan becomes a Run, at `POST /research/{id}/start`. `refine` called with neither `answers` nor `feedback` is the mandated skip/start-now affordance (`DR-1.6`) — it forces straight to a plan without a second clarify round.
    - **Phases map onto the existing, frozen event vocabulary — no new event types.** Each pipeline phase (planning/searching/reading/analyzing/writing) is one `step.started`/`step.completed` pair; a newly-used source lands a `citation.added` (also the report's `[n]` numbering); once per round, `tool.progress` carries cumulative run-wide "N sources, M findings"; the `DR-4.1` two-consecutive-empty-rounds abort is a `limit.notice` immediately followed by the run ending in `error` with that message verbatim. `runs/events.py` was not touched.
    - **Report persistence is decoupled from the orchestrator's own task.** `start` registers a waiter future for the Run's id (the same `app.state.*_run_waiters` shape the scheduler's agent-task executor already uses) and a background task awaits genuine Run-terminal before writing the finished report/stats/status — so a cancellation mid-write can't corrupt the persisted row. "Continue in chat" (`DR-1.5`/`DR-7.3`) reuses `ConversationStore.record` verbatim (a synthetic user-prompt/report exchange seeds the new conversation) rather than inventing a document-attachment seam; a repeat call is idempotent off `ResearchRun.conversation_id` already being set.
    - **Notifications get their own policy branch, not a bolt-on.** Research runs are conversation-less, so D30's conversation-linked emit policy doesn't apply; `_notify_run_terminal` branches on `run.kind == "research"` and fires `run_completed`/`run_failed` unconditionally (never subscriber-gated — a multi-minute run finishing is worth knowing about even mid-tab), carrying a new nullable `research_id` (additive column on `Notification`, threaded through the same D30 machinery) that deep-links back to the research entry.

- **D20 — Sensitive-capability gating 🟢 DECIDED: approval via Pydantic AI deferred tools.** Sensitive tools (Axis B in D14) are gated by **explicit user approval**, implemented with Pydantic AI's human-in-the-loop deferred-tools mechanism:
  - A sensitive tool is marked `requires_approval=True` (or raises `ApprovalRequired` for runtime-conditional sensitivity — e.g. a write to a protected path).
  - The agent run ends with a `DeferredToolRequests` output whose `approvals` list holds each pending `ToolCallPart` (tool name + **validated args** + `tool_call_id`). Pydantic AI has done the agentic work; it has *not* executed the call.
  - **We own the pause/resume lifecycle:** the Run enters an `awaiting_input` state; we emit an `approval_required` event (carrying the human-readable action + args) over the stream; we notify on the appropriate channel (inline for an interactive Run; push/email for an unattended/scheduled Run); we hold the serialized message history.
  - The user decides via a `POST /runs/{id}/approve` control endpoint. We resume the agent with `deferred_tool_results=DeferredToolResults(approvals={tool_call_id: ToolApproved() | ToolDenied(message=…)})`. `ToolApproved` may carry `override_args`; `ToolDenied`'s message is shown to the model so it can adapt.
  - Because the parked state is just serialized history + pending requests, an approval pause **naturally survives client disconnect** (`AE-7`) and can outlive it entirely for unattended runs.

  This unifies interactive and unattended gating under one mechanism (only the notification channel and latency differ) and keeps the clean split: Pydantic AI decides *what* needs approval and *exactly what it would do*; we own *parking, notifying, waiting, and resuming*.

- **D21 — Document streaming & auto-promotion (`AE-6.2`, `AE-6.4`, `DOC-3`).** How AI-authored document content streams into a version and commits, and how a substantial inline code/doc block gets *promoted* into a real document automatically. Detection heuristic + event shape. **Defer until the document feature is in scope.**

- **D22 — Upload ingestion / extraction pipeline (`UP-*`, `RAG-4`) 🟢 DECIDED: a pluggable extractor seam, MinerU-in-front with a built-in floor.** An uploaded file is stored sealed (bytes + filename + extracted text), and its *contents* are made usable by extracting a text layer off the request path on a lock-aware worker, then chunked into the shared corpus so the agent retrieves it via `corpus.retrieve` (`services/uploads` + `services/corpus/uploads`, mirroring documents). Duplicate recognition is a content `sha256` (`UP-1`); the upload endpoint is rate-limited (`UP-4`, `core/ratelimit`).
  - **Extraction is a seam (`UploadExtractor`), not one path.** The **built-in** `BasicExtractor` is the zero-setup floor: pypdfium2 pulls native PDF text, and a page with no text layer (scanned/image-only) is rasterized and sent to a **vision model** for OCR — the codebase's first multimodal model call, kept in the engine layer (`agent/vision.py`) behind a narrow `VisionOCR` seam so the services-layer extractor never imports the engine (the registry resolves a vision-capable endpoint; absent ⇒ the page comes back empty *with a reason*, an actionable error the operator can retry). **MinerU** (`services/upload_mineru`) is the high-fidelity path — layout, tables, formulas → clean Markdown — and is **detected, not bundled**: like the container runtime and SearXNG it's a host capability found with `shutil.which` and shelled out to, so the project venv never pulls its PyTorch stack. It runs as a **transient subprocess** (models load per-extraction, freed on exit — lazy + auto-offload by construction). `FallbackExtractor` puts MinerU in front of the built-in and degrades to it on *any* failure (missing, OOM, timeout), matching the fail-soft posture. The producing extractor (`basic`/`mineru`/`manual`) is recorded on each upload so a built-in extraction is identifiable and re-runnable for higher fidelity — and since the original bytes are retained sealed for the upload's lifetime, that re-run reads from the same source (a labelled `retry`).
  - **Deferred.** `UP-3` fillable-form detection; the chat-attachment path (a turn's inline file/link context, `CHAT-2`) reuses this extraction but its wiring lands with chat attachments.

- **D26 — Extraction/model resource governor (`UP-*`, `COOK-*`) 🟠 DEFERRED: documented, not built.** MinerU's models and the operator's LLM compete for the same host memory/VRAM. Today this is sidestepped by running MinerU as a **transient subprocess** (D22) — its models exist only during an extraction and are freed on exit, so co-residency is bounded by construction and needs no governor for correctness; on the target unified-memory hardware (128 GB Apple Silicon) contention rarely binds. The governor is the *performance* layer for when it does:
  - **Warm + reap.** Optionally keep a MinerU server warm for fast repeat extractions, lazily loaded on first use and offloaded after an idle TTL — the **sandbox-session reaper pattern** (D23) applied to an extraction model.
  - **Headroom-aware scheduling.** Extend the Cookbook's host hardware detection (`COOK-*`) with the extraction pipeline's footprint and live free headroom, to decide whether MinerU and a model can co-reside, and to **serialize** heavy jobs under pressure.
  - **Extraction precedence — bounded by what we own.** Under genuine pressure an upload extraction should win. We can stop/reload a **locally-served** model (the system owns its lifecycle — `model serve/stop` is already a sensitive action) to free room; we **cannot** evict a **remote** endpoint (another host, not ours) — there it's pure contention or none. So "extraction takes precedence" means: prioritize extraction in a host-resource scheduler and, where the model is locally served, free it; never claim to evict what we don't control.

- **D23 — Code-execution isolation (`XC-SEC-7`, `AE-2`, `AE-3`) 🟢 DECIDED: sandboxed by default, host only via explained approval.** Approval (D20) is *consent, not containment* — a misjudged click, a destructive command dressed up as benign, or injection that manufactures a plausible approval request all land on the real host. So code execution gets a structural boundary *underneath* the gate, not just the gate.
  - **Invariant.** All agent-invoked code and shell execution runs in an environment **isolated from the host**, operating only on **copies** of the files explicitly handed to it. It cannot read or modify the host filesystem, processes, or environment. Outputs return to the user/app explicitly; any write-back to real data is an ordinary, separately-gated action — nothing escapes the box as a side effect.
  - **Two paths, cleanly split.** (a) **Sandboxed execution** is the default and is *not* approval-gated — being contained, it carries no host-level risk, so the agent computes freely in the box (and routine code-exec loses its approval friction entirely). (b) **Host execution** is a distinct, **approval-gated deferred tool** (reusing D20's mechanism) for the legitimate case where the user genuinely needs the host itself changed; its approval request MUST carry a **plain-language explanation** of what the code does and its effect, not just the raw command (`AE-3.4`).
  - **Operator's own terminal stays.** The manual Host Shell (`SHELL-*`) is operator-initiated — the operator deliberately operating their own machine — and is unchanged by this; the agent can never reach it. The agent's only path to the host is the explained-approval tool above.
  - **Mechanism — pluggable, container default.** An **execution-sandbox capability** in `services/` with a pluggable backend; default is a **container runtime** (Docker/Podman) providing filesystem/process/network isolation and copy-in/copy-out of files. Provider-agnostic like the vector store (D18); the container runtime is the portable default that satisfies `XC-PORT-1` (works across Linux/macOS/Windows, no OS-specific facility).
  - **Degradation — fail closed, never to host.** If no sandbox runtime is available, the code-execution capability is **disabled** and the agent is told so (`XC-DEG-*`); it MUST NOT silently fall back to running on the host. Network egress from the sandbox is off/controlled by default so copied data can't leak; tighten per config.
  - **Ripples.** The `approval.required` event gains an optional explanation field for the host-exec case (additive to the frozen v1 protocol, D15 — no version bump). `RUN-1`'s in-browser snippet runner already honors the spirit (never on host) and is unaffected. `SHELL-*` is reframed to the operator's own deliberate terminal — agent-unreachable, opened only through a re-authenticated **host mode** (`SHELL-3`).
  - **As built — `services/sandbox/` + the `code` toolset.** The capability is a package: `base` (the `Sandbox` ABC + `SandboxSpec`/`SandboxResult`/`SandboxFile` value types + `SandboxError`), `container` (the default `ContainerSandbox` backend), `host` (the deliberate non-sandboxed escape hatch), and `detect` (the fail-closed factory). `ContainerSandbox` drives the Docker/Podman CLI over `asyncio` subprocesses (no SDK dep — keeps the dependency surface small and portable): each run is a throwaway container with `--network none` (egress off unless asked), `--cap-drop ALL`, `--security-opt no-new-privileges`, a read-only root with a writable `/work` bind-mount + small tmpfs, and explicit memory/CPU/PID caps; only `spec.env` reaches the process (the host env never leaks). Copy-in/out is a host-side temp dir mounted at `/work` (the controlled copy area — the operator's real files are never mounted), with a `../`-escape guard. `detect_sandbox` probes the runtime once at startup and returns `None` when none is present or the operator disabled it (`sandbox_enabled`) — the capability is then **absent**, never a host fallback. The handle lives on `app.state.sandbox`, threads through the chat/resume orchestrators onto `RunDeps.sandbox_sessions`, and is reached by the `code` toolset: `execute_code` (sandboxed `python`/`bash`, **not** approval-gated; reports "unavailable" and refuses to run when no runtime) and `run_host_command` (the host path, `requires_approval=True`, taking a `command` + a plain-language `explanation`). The engine lifts any approval tool's `explanation` argument into the new optional `ApprovalRequired.explanation` field so the operator sees it as a distinct field, not buried in raw args.
    - **Continuity — a per-conversation live session (`session`).** Rather than a throwaway container per call, the `code` toolset reaches a `SandboxSessionManager` that keys one live container to the conversation, **lazily** created on the first execution and kept warm so the agent can iterate against the same process and filesystem (fix-and-rerun, reuse a just-installed dependency) without rebuilding. A background reaper kills a session idle past `sandbox_session_idle_ttl_s`. Files survive the reap: the workspace is a host-side dir bind-mounted into the container, and on reap it is **sealed with the vault** (the agent's own files and outputs — virtual environments and language caches are excluded as cheap-to-rebuild bloat) and the plaintext removed, then restored on the next run — so continuity is durable and encrypted at rest, while only the live process/system state is rebuilt. Egress stays off-by-default without a fragile live toggle: ordinary calls `exec` into the no-network session container; a `network=True` call runs as a one-shot `--network bridge` container over the *same* workspace, so a fetched package lands in files the session then sees. This live-process foundation is also what later enables previewing an agent-run server or generated artifact in the frontend. Pre-authorization (D24) has since landed with the task scheduler; the external-tool trust allowlist (D25) is **not** built yet — it lands with MCP/INTEG.

- **D24 — Pre-authorized scheduled tasks (`AE-3.5`, `TASK-*`) 🟢 DECIDED: approval moves to scheduling time as a scoped standing grant.** Strict per-run approval (`AE-3.2`) makes a recurring task that touches a sensitive action **park every run** — defeating the point of unattended automation. Resolution: **the scheduling tool is itself a deferred/approval tool** (D20). When the agent schedules a task, the Run parks and surfaces the task to the operator — its trigger, intended actions, and the specific **sensitive actions** it would perform — and approval grants a **scoped pre-authorization** stored with the task.
  - **At each unattended run.** A sensitive action **within** the pre-authorized scope is auto-satisfied (the deferred result is supplied as approved) without re-parking; a sensitive action **outside** the scope falls back to `AE-3.2` (pause + notify). The standing-trust surface is bounded to exactly what the operator reviewed.
  - **Scope, not a blank cheque.** The pre-authorization is over a **declared scope** (e.g. 'may send email to these recipients', 'may run sandboxed code', 'may not run host code'), checked at runtime — not an unconditional pass. For free-form agent tasks whose exact calls aren't known at scheduling time, the operator approves the *bounds* and runtime actions are matched against them; an out-of-bounds action pauses.
  - **Revocable & visible.** The operator can review and revoke any task's pre-authorization at any time; revocation returns the task to strict per-run approval. Ties D13 (the scheduler materializes tasks as Runs) to D20 (the deferred-tool approval mechanism), reusing both rather than adding new machinery.
  - **As built — the scope rides D28's conversation-grant mechanism, not a parallel one.** `ScheduledTask.pre_authorized` (`list[str]`, stored in the clear — policy, not content, like `ApprovalGrant.tool_name`) reuses the exact tool-name vocabulary `AE-3.7`'s conversation grants already use, validated on write (`routes/tasks.py`'s `_validate_pre_authorized`; an unknown scope value is rejected on create/patch, never silently dropped). At each execution the scheduler's composed executor seeds a fresh conversation grant from that scope with a TTL covering the run, so `agent/engine`'s existing D28 auto-approve split is what actually satisfies an in-scope deferred call — no second approval code path exists. A sensitive action outside the scope falls through that same split to a strict park (an `approval_needed` notification, identical to an interactive run) — verified end-to-end by `test_task_run_hitting_sensitive_tool_outside_grants_parks_and_notifies`. Revocation is just editing `preAuthorized` via `PATCH /tasks/{id}` (no separate revoke endpoint); the next execution seeds from the edited scope. The unattended-run notification channel for a task's outcome (`TASK-6`) is **in-app only in v1** — email/push are deferred (see D30).

- **D25 — External-tool gating (`AE-3.6`, `MCP-*`, `INTEG-*`) 🟢 DECIDED: sensitive by default, operator trust opt-out.** The `AE-3` sensitivity model rests on a *known* list (shell, email, vault…); tools from registered MCP servers and configured third-party integrations are the **unknown** case it can't enumerate — arbitrary, possibly externally-visible effects. So they are **approval-gated by default**, and the operator opts specific tools into **trusted** (auto-approve) status. Consistent with the rest of the posture (sandbox-by-default, explain-before-host): unknowns are contained until the operator deliberately relaxes them, per tool, never the agent.
  - **Mechanism.** In the toolset stack, external tools carry a default *sensitive* marking and ride the same deferred-tool approval path as D20; a **trusted-tool allowlist** (operator-managed, persisted in encrypted settings) flips specific tools to auto-approve. Enable/disable (`AE-3.3`) is orthogonal and still applies.
  - **Scope.** Trust is **per tool, not per server**, so registering/enabling a server doesn't blanket-trust everything it exposes. Revocable at any time.

- **D27 — Web page fetch (`SEARCH-2`, `DR-*`) 🟢 DECIDED: always-render in a containerized headless browser, extract with trafilatura.** The agent's `fetch` capability was a static `httpx` GET + trafilatura. A static GET never runs JavaScript, so SPAs and client-rendered pages came back empty — a direct failure of "read what's on the page." A "static-first, retry with a browser if thin" tier was rejected: reliably *detecting* an incomplete static extract is an unreliable heuristic. So the **open web is treated as always-dynamic** — every fetch renders the page in a real browser, then the rendered DOM is extracted. Lives in its own capability, `services/webfetch/` (browser · guard · extract · stealth · fetcher), separate from `services/search` (SearXNG).
  - **Engine — in-process-driven, but the browser is containerized.** Firecrawl was evaluated and declined: self-hosted it adds only a headless browser behind a heavy Node/Redis/Postgres stack with an un-tunable, historically-buggy SSRF guard (AGPL); cloud-hosted it breaks the local-first posture (egress + key + cost) and is the only tier with real anti-bot/proxy reach. We render with **Playwright driving a headless Chromium that runs in its own loopback-bound container** (the same Docker/Podman runtime as the sandbox and SearXNG), connected over the **Chrome DevTools Protocol** (`connect_over_cdp`). Rendering executes *untrusted page JavaScript*, so it must not run in the backend process; the container isolates it, and the container's separate network namespace means even an SSRF-guard bypass (a timed DNS rebind) can't reach the host's own loopback services. CDP is version-tolerant, so the image tracks **`:latest`** (refreshed each boot by the shared `ensure_image`, like SearXNG) without being pinned to the Python client's Playwright version — and there is **no local browser binary to install**. Bring-up mirrors `ManagedSearxng`: best-effort, non-fatal, background; absent a runtime/image the capability degrades, never blocking startup.
  - **Extraction — trafilatura is the extractor, not the fetcher.** Independent benchmarks put trafilatura first among open-source main-content extractors; it runs over the rendered HTML string, emits Markdown natively (tables/links/code), and internally cascades (its heuristics → readability-lxml → jusText). The earlier sketch of Readability.js + a Markdown converter was dropped: Readability flattens tables and is weaker on structured pages, and trafilatura's native Markdown removes the converter. When trafilatura returns nothing usable, the page's rendered `innerText` is the fallback — a genuinely different failure mode (non-prose pages) that guarantees non-empty output when visible text exists. LLM-based extractors (Jina ReaderLM) were rejected: slower, costlier, and not more accurate per current benchmarks.
  - **SSRF — every request, not just the entry URL.** The entry URL is pre-flighted with `core.ssrf.assert_public_url`; then a `page.route` handler re-runs the **same** guard on every request the browser makes — main document, redirects, and subresources — reusing the existing primitive rather than re-deriving it. A blocked main-frame navigation is a hard refusal (`SSRFError`) on every code path; subresource blocks are silent. `data:`/`blob:`/`about:` are in-memory and allowed; any other non-http(s) scheme is refused. Strictly stronger than the old manual per-redirect-hop loop.
  - **Stealth — present as a normal user's browser.** A headless automated browser leaks tells (`HeadlessChrome` UA, `navigator.webdriver`, empty plugins, a SwiftShader WebGL renderer) that make sites serve bot/blocked/stripped content, so the agent wouldn't see what a person sees. Each context gets a realistic UA (matched to the engine version), a normal locale/timezone/viewport/Accept-Language, and an init script masking those tells. This is **fingerprint normalization, not anti-bot evasion** — it gets ordinary sites to return real content; it does *not* defeat residential-proxy/CAPTCHA walls (the cloud tier we declined).
  - **Container hardening.** The browser container runs untrusted code, so it is hardened like the sandbox: `--cap-drop ALL`, `--security-opt no-new-privileges`, a **read-only root** with a tmpfs for Chromium's only writable path, memory/PID/shm caps, loopback-only published CDP port. It runs as container-root (the image is built for it) with all capabilities dropped.
  - **Deferred follow-ups (documented, not built).** (a) **Shared managed-container base.** `ManagedBrowser` and `ManagedSearxng` now duplicate the "managed loopback container with best-effort background bring-up" lifecycle (start/stop/`_bring_up`/`_flags`), and the two flag sets have already begun to drift. The right altitude is a shared `ManagedContainer` base in `services/sandbox` owning the lifecycle, with each as a thin specialization supplying image/name/flags + a readiness hook — deferred because it touches the landed SearXNG path. (b) **Egress-level SSRF defense-in-depth.** The per-request route guard remains TOCTOU-exposed to a timed DNS rebind (the connect re-resolves independently); the container netns already prevents reaching host loopback, but the `--network bridge` container can still egress to the LAN/metadata endpoint. Dropping private CIDRs at the container's egress (a filtering resolver / an allowlisted proxy) would make the in-process guard defense-in-depth rather than the sole boundary.

- **D28 — Conversation-scoped auto-approval grants + gating global knowledge-base recall (`AE-3`) 🟢 DECIDED: a generic, operator-opt-in standing grant over the deferred-tool mechanism, off by default.** Two operator-driven additions to the approval surface (D20), built once as a tool-agnostic layer:
  - **Global corpus recall is now an approval gate — a *context* gate, not a *security* one.** `corpus.retrieve` pulls untrusted knowledge-base content (folders/memory/conversations/uploads) into the model's context; when the agent judges the KB relevant but the operator knows it isn't, the operator should be able to keep that content out of the window. So **global recall** (no `source_ids`) is gated by raising `ApprovalRequired` — a *conditional* gate (D20's runtime-conditional path), so an **explicit-id read** (a file the operator just attached, whose id rides in the attachment marker) passes straight through; gating a file the operator deliberately provided would be pure friction. A denial returns `ToolDenied` and the retrieval never runs, so nothing reaches context. This is deliberately **outside** the `AE-3.1` sensitive-action set (it is read-only, no host effect) — it is the first gate motivated by *context hygiene* rather than irreversibility, and the spec marks it as such.
  - **A conversation-scoped, time-limited, revocable auto-approval grant.** Re-prompting for the *same* deferred call across a long run is the friction `AE-3.5` already solved for scheduled tasks; this is the interactive analogue. When the operator approves a deferred call they may opt into "allow for the rest of this conversation" (the affordance **appears on every** deferred approval but is **off by default** — the strict per-call default is unchanged). A grant is keyed `(owner, conversation, tool)`, carries a **TTL** (`approval_grant_ttl_s`, default 24h), and is **visible + revocable** on the conversation. While a grant is active the engine resolves that tool's deferred requests itself — `DeferredToolResults(approvals={…: ToolApproved()})` — without an operator round-trip; the tool still streams its normal `tool.started/completed` events, so an auto-approved call stays visible in the transcript.
  - **Eligibility — any gated tool, by the operator's explicit choice.** Unlike `AE-3.5` (scoped to the *specific* sensitive actions a task declares) and `D25` (per-tool trust for *external* tools only), this grant can cover **any** deferred tool, including `AE-3.1` sensitive actions such as host execution. This is a deliberate **relaxation of `AE-3.1`'s strict per-call rule for sensitive actions**, made on the single operator's instruction and bounded three ways: it is **opt-in** (never defaulted on), **conversation-scoped** (never global), and **time-limited + revocable**. The security trade-off is real — a standing grant for host execution auto-runs further host commands in that thread until it lapses or is revoked — and is accepted here because the operator chose it knowingly; the bounds keep the blast radius to one conversation for one day. `AE-3.1`/`AE-3.7` are edited in place to reflect this.
  - **As built — one mechanism, both sides.** Backend: a persisted `ApprovalGrant` (owner seam, no sealing — it is policy, not content) + an `ApprovalGrantStore` (grant/active/list/revoke, TTL-filtered) on `app.state`; one central split in the engine's `DeferredToolRequests` branch (auto-approve the granted calls — resume inline when *all* are granted, else park only the rest with the auto ones pre-filled and merged on resume); `ApprovalDecision.scope` on `POST /runs/{id}/approve` records the grant; `GET`/`DELETE /conversations/{id}/grants` for the visible/revocable list. Frontend: one opt-in checkbox on the shared `ApprovalCard` (renders for every deferred call) + a revocable grants strip on the conversation. No per-tool work beyond marking `corpus.retrieve`'s global path.

- **D29 — Unify artifacts + live previews into one versioned "View" 🟢 DECIDED: one tool, one surface; head = live server, history = snapshots.** The agent had two ways to show its output — `publish_artifact` (a frozen file snapshot, encrypted + served inert) and `start_preview`/`stop_preview` (a live reverse-proxied server) — exposed as two tools, two event types, and two inline UI panels. That split is a *mechanism* (a frozen file vs. a running process) leaking out as if it were two products: it confused the model into double-showing the same page (serve it live *and* re-publish it as an artifact), and the live preview pointed at the server root, so `python -m http.server` with no `index.html` rendered a **directory listing** instead of the page. The operator's framing collapses them: the useful things are **a live view of the current thing** and **the ability to flip back through previous versions to compare**. Those are the **head** and the **history** of one surface — and crucially a live server has *no* history, so the comparable timeline can only be snapshots. So artifacts aren't a rival feature; they are the versioning mechanism for the one **View**.
  - **One capability, two mechanisms underneath.** A single `view` toolset: `view_show(file=…)` captures a static **version** (reusing `services/artifacts` as the version store — no schema change) and emits `view.version`; `view_show(serve=…, port=…, path=…)` runs the live **head** (reusing `services/sandbox` + the `/previews/{token}/` proxy) and emits `view.live`; `view_close` emits `view.live.stopped`. Exactly one of `file`/`serve` per call (else `ModelRetry`). The model now reasons about one thing, so the redundant double-show goes away.
  - **The directory-listing fix falls out of the unification.** `view_show(serve=…)` takes an optional `path` (the entry file) and bakes it into the proxied url (`/previews/{token}/<entry>`), so the live head renders the page, not the autoindex. The frontend renders the url verbatim — no client logic.
  - **One UI surface.** The transcript shows compact **chips** where the View changed (a version added, the live head started); the heavy render moves to the **viewport** beside the conversation — the current item on stage plus a version timeline to flip back and compare. The viewport auto-opens the first time a thread produces a View item, then respects a manual close (first-time-only, per thread). Cold reads re-attach static versions to their message (warm/cold parity); a stopped live head isn't re-openable, by nature.
  - **Scope of the rename.** The *product surface* unifies — tool (`view_show`/`view_close`), events (`view.version`/`view.live`/`view.live.stopped`), REST (`/views/*`), and frontend vocabulary. The internal `Artifact` table + `ArtifactStore` stay as the version store (the snapshots are already sealed + `created_at`-ordered, so no migration), and the security-sensitive token-credentialed live proxy stays at `/previews/{token}/`. Deferred: side-by-side version diff, search/filter in the viewport, persisting a live head across session reaps.
  - **🔧 REVISED — `show` anchors the version; one version per show, not two systems.** D29 left *two* version mechanisms racing: `view_show(file=)` minted an **artifact** version mid-turn (`view.version`), while the later-added git-style **workspace-history** store (`services/workspace_history`, `view.snapshot`) blindly captured the whole sandbox tree at *end-of-turn* — so a turn that both showed a result and wrote a file produced two disjoint "versions" the UI couldn't reconcile (e.g. a plot image artifact + a code-only snapshot of the generator script, the latter stealing focus and rendering "NO PREVIEW"). The fix collapses them: **a version IS a workspace snapshot, and `show` is the sole creator of versions and the anchor of each version's preview.** `view_show(file=)` captures the workspace tree (the version's *code*) and stamps a **preview descriptor** (`preview_artifact_id` + `preview_kind`) pointing at the shown file's bytes (still the artifact store, now purely *preview bytes*, not a rival version); `view_show(serve=)` captures a version with a live/auto preview overlaid by the head. The blind end-of-turn auto-capture (`agent/engine._capture_workspace_snapshot`) and the `view.version` event are **removed**; `view.snapshot` carries the preview descriptor and is the one version event. Consequence (intended): turns that change files but never `show` are no longer versioned — the git-style history is now anchored to *what was shown*, not every turn. Known limit: a live head's CODE is frozen at show-time until the next `show`.

- **D30 — Attention/notification surface (`AE-3.2`) 🟢 DECIDED: a second, separately-versioned SSE surface; subscriber-count-gated completion notices; write-behind persistence via an injected terminal hook.** `AE-3.2` needs the operator to learn about approvals, failures, and completions while roaming the app or away entirely — a durable, cross-conversation concern the frozen per-run protocol (D15) was never shaped for: that stream is per-run, in-memory-only, and dies with its run, so a run the operator wasn't attached to leaves no trace once it ends.
  - **A new surface, not a new event on the old one.** Rather than extend the run union, notifications get their **own** REST + SSE surface (`routes/notifications.py`, `services/notifications.py`, `models/notification.py`) with its **own** versioned envelope (`notification.created`/`notification.updated`) and its **own** in-memory ring buffer keyed by a **per-process** `seq` — deliberately mirroring the run transport's framing (`id:` seq, flat JSON `data:`, `Last-Event-ID` resume, ~15s keepalive) rather than sharing its buffer, registry, or lifetime. Cost: two SSE stacks with parallel-but-separate reconnect/replay logic instead of one generalized transport. Accepted because the run union is explicitly frozen (D15) and because the two have genuinely different lifetimes — a run's buffer dies with the run; the notification ring buffer lives for the process and is separately backed by the DB for real history (REST `GET /notifications` backfill), which no per-run stream needs.
  - **`run_completed` is gated on subscriber count, not on any explicit "did the operator see this" signal.** A run that finishes while nobody is attached to its own event stream is the case `AE-3.2`'s "pause unattended" is really about; a run finishing while the operator is watching it stream in real time needs no separate notification — they already saw it. The registry's injected `on_terminal` hook captures `run.stream.subscriber_count > 0` **synchronously, at the terminal transition**, before scheduling the (async) notify task — reading it later, from inside the scheduled task, would race the stream's own subscriber cleanup and could observe a stale count. `approval_needed` and `run_failed` have no such gate: an approval always needs a decision and a failure is always worth surfacing, watched or not. `limit.notice`/`context.window` are deliberately never notifications — in-band-only signals, not attention-worthy on their own.
  - **`runs/` stays free of a `services/` import via one injected callback.** The layer rule (`routes → agent/research → tools → services → core`, `runs/` as the substrate underneath all of it) would break if the registry reached up into `services/notifications` directly. Instead `RunRegistry` takes an optional `on_terminal: Callable[[Run], None]` at construction — synchronous, best-effort, swallowing its own exceptions so a notification failure can never affect a run's own recorded outcome — and `app.py` supplies the closure that does the actual `services/` work (resolve the linked notification, then notify per the policy above). The registry only ever knows it holds an optional callback; the composition lives in the assembly layer where both sides are already visible.
  - **Persistence rides the same write-behind discipline as conversations (D8), as its own drainer instance.** `NotificationService` owns a second `WriteBehindWorker` (`core/worker.py` — the same lock-aware drainer conversations use, not a shared instance) so a locked vault parks a pending write instead of losing it, and title/body encryption happens only in the drainer, off the request/emit path. Read/resolve mutations ride the same queue as creation, so ordering between "created" and "resolved elsewhere" is preserved without a separate mutation path.
  - **Auto-resolution is multi-path by construction.** An `approval_needed` notification's `resolved_at` is set whichever way the underlying approval is actually settled — the approve route, a deny, a conversation-grant short-circuit (D28), or (the backstop) the run simply reaching terminal with the approval never decided (e.g. cancelled while parked). The terminal hook always calls `resolve_for_run` first, unconditionally, before considering whether to also emit a completion/failure notice — so a dangling `approval_needed` can never survive its run.
  - **Encryption granularity matches the rest of the app (D17), not a stronger or weaker posture.** `title`/`body` are the content and are AEAD-sealed per column; `kind`, the `conversation_id`/`run_id`/`task_id` links, and timestamps stay structural/plaintext so the DB can index, order, and filter (`unread_only`, pagination) without decrypting rows just to list them — the same trade-off already made for conversations and documents. `task_id` was a nullable forward-compat seam at this decision's writing and is no longer unwritten: the task scheduler (D13) now stamps it on every `reminder` and `task_outcome` notification (`app.py`'s `_task_notify`/`_task_executor` closures), the same way the research surface (D19) stamps the analogous `research_id`.

- **D31 — Operator Shell transport + re-auth (`SHELL-1..3`, `RUN-1`) 🟢 DECIDED: WebSocket for the PTY, a short-TTL single-use host-mode token as first-message auth.** Two builds landed together — the operator's own host terminal and the in-browser code runner — each resolving a different question the house patterns (D1's SSE+POST, D20's approval) don't answer cleanly.
  - **Deliberate WebSocket exception to the house SSE+POST pattern (`SHELL-1`).** D1 fixed the run transport as SSE-down/POST-up because a Run's shape — one server-driven event stream, occasional client control calls (`approve`, `cancel`) — never needs client→server payloads on the hot path. A PTY is the opposite shape: **bidirectional and keystroke-latency-sensitive**, with every keystroke and every resize a client→server message that must interleave with server→client output on the same connection. Modeling that as per-keystroke POSTs against an SSE stream would add round-trip latency to every character and require a second correlation mechanism for ordering; a single WebSocket carries both directions on one ordered connection, which is the transport the shape actually calls for. This is scoped to the shell — the Run substrate's SSE+POST contract (D1, D15) is unchanged and stays frozen.
  - **Host-mode re-auth is a fresh, short-TTL, single-use, constant-time-compared token (`SHELL-3`).** The global ASGI auth gate (`core/auth`, `XC-SEC-1`) only guards the **http** scope; it does not run on a WebSocket upgrade, so `/shell/ws` needed its own gate rather than inheriting one that silently doesn't apply. `POST /shell/host-mode` re-verifies the operator's password (`core.vault.verify_password` — a verifier-only check, no unlock side effect) and mints a single-use token with a short TTL; the token is required as a field in the **first WebSocket message**, checked with a constant-time comparison (mirroring `tasks.py`'s webhook-token pattern) before the PTY spawns. Single-use + short TTL bounds a leaked token's blast radius to one session opened within seconds of minting; re-verifying the password (rather than trusting the standing session cookie) means holding an open browser tab is not sufficient to reach a host shell.
  - **Agent-unreachable by construction, not by convention (`SHELL-2`).** `services/host_shell.py` is imported only by `routes/shell.py` and `app.py`'s wiring — never by anything under `tools/`, `agent/`, or `research/`, so there is no code path by which the agent's tool catalog could reach a live PTY. This is a stronger guarantee than a runtime check: a regression would have to *add* an import to introduce the hole, which `tests/test_shell_guard.py` catches by grepping every tool/agent/research module for `host_shell`/`ShellService` and failing if either name appears. The agent's only host-affecting path remains `run_host_command` (D23) — explained, approval-gated, and structurally distinct from the operator's own terminal.
  - **Kill-on-lock, not park-on-lock.** Unlike the scheduler (D13) and corpus indexers, which **park** while the vault is locked because their work is resumable, a live PTY session is holding open a real host process on the operator's behalf — parking would leave a shell session alive and unattended across a lock event, which is the opposite of what locking is supposed to guarantee. `ShellService` instead registers an `on_lock` callback (`core.vault`'s new callback registry, each wrapped in try/except so one failing subscriber can't block the lock) that calls `kill_all()`, terminating every live session (SIGHUP-then-SIGKILL grace teardown, closing the socket with 4423) synchronously at the moment the vault locks.
  - **RUN-1 stays out of this entirely — no host, no backend round trip.** The in-browser snippet runner (`RUN-1`) is unrelated to the shell's transport/auth questions by design: HTML/JS execute in a blob-URL iframe via the existing `SandboxedFrame` (`sandbox` attribute, no `allow-same-origin`), and Python runs in a self-hosted Pyodide build inside a dedicated Web Worker — both entirely client-side, never touching the host filesystem or the backend process. This is the frontend-only counterpart to D23's "sandboxed by default, host only via explained approval": `RUN-1` isn't sandboxed-on-the-host, it's *not on the host at all*, so it carries none of `SHELL-*`'s re-auth or agent-reachability concerns.
  - **Frontend mirrors the same discipline as the run stream, deliberately without its give-up budget.** `lib/stream/notificationStream.ts` reuses `runStream.ts`'s fetch-SSE/`Last-Event-ID`/backoff/watchdog pattern but retries indefinitely (capped backoff) rather than giving up after a budget — the attention stream is meant to be live for the app's whole session, not just the life of one run a user is actively watching. `lib/stream/notificationEvents.ts` is a typed mirror of the backend envelope, kept in lockstep the same way `lib/stream/events.ts` mirrors `runs/events.py` — a second instance of that discipline, not an exception to it.

- **D32 — Skills as portable Agent Skills bundles (`SKILL-1..3`) 🟢 DECIDED: the open standard *is* the data model; `published` is the trust boundary; three levels of disclosure, with the bundle staged into the sandbox.** `SKILL-*` asks for reusable know-how the agent accumulates and applies. The tempting build is a bespoke table — a title, a body, a list of trigger phrases (exactly what the mock frontend modeled). That would have worked and would have been strictly worse, because a skill is the one artifact in this system with an obvious *external* life: the operator already has skills written for other tools, and the ones they write here are worth taking elsewhere. So the format is not ours to invent. A skill here is an **Agent Skills** bundle (agentskills.io — what Claude Code, claude.ai uploads, and the Skills API all read): a `SKILL.md` with YAML frontmatter plus its supporting files, imported and exported unchanged.
  - **The standard is the schema, and compliance lives in one pure module.** `services/skills/bundle.py` has no database, no vault, and no disk — it turns bytes into a validated `ParsedSkill` or refuses with the offending *field* named, and renders one back out. Every other layer is a caller: `SkillStore.create`/`update` re-run the same validators, so a skill written through the REST API is exactly as standard-compliant as one imported from a zip, and neither the routes nor the agent's tools can produce a bundle that wouldn't survive an export. The constraints enforced are the standard's, not ours (`name` ≤64 chars and `[a-z0-9-]` with `anthropic`/`claude` reserved, `description` ≤1024 and XML-tag-free, `compatibility` ≤500, one top-level directory matching the name, ≤30 MB uncompressed).
  - **Round-trip fidelity is *semantic*, not byte-exact — stated rather than glossed.** The six portable fields round-trip through typed attributes; every other frontmatter key (Claude Code extensions like `when_to_use`, `paths`, `argument-hint`) is preserved verbatim, in its original order, in a sealed `extras_json_enc` — dropping unknown keys would silently degrade a bundle on its way through us, which is the precise failure that makes a format non-portable. What is *not* preserved is YAML comments and quoting style, because we re-render rather than splice. Supporting files are always byte-identical. The test that pins this (`test_claude_code_bundle_roundtrip`) imports a realistic bundle, exports it, and re-imports it — that assertion, not the prose here, is the actual contract.
  - **Decomposed into two tables, not one sealed zip blob.** An `Upload` stores a single opaque `blob_enc` because an upload *is* opaque; a skill is structured, and all three requirements need its parts addressable. The per-turn catalog (`SKILL-2`) reads name+description without touching a single file byte; the surgical edit (`SKILL-3`) needs the instruction body as its own column; staging into the sandbox writes files straight through with nothing to unzip. `SKILL.md` is deliberately **not** a `skill_files` row — it is `body_enc` plus the frontmatter columns, rendered on demand, so the stored body and the exported artifact cannot drift apart. Cost: import unzips once, and export re-renders. Accepted.
  - **`published` is a security boundary, not a display state.** A skill is instructions the agent will follow, so an imported bundle is *inert* until a human has read it: `import_bundle` always lands `published=False, source="imported"`, and the catalog the model sees lists published skills only. `get_by_name(published_only=True)` makes a draft indistinguishable from a skill that doesn't exist — the agent is never told there is work in progress it might ask about. The agent's own `skills_create` writes drafts too, always; publication is the operator's act and nothing the model can do reaches the catalog on its own. That is also precisely the seam `SKILL-4` (auto-publishing high-confidence recoveries from the `AE-5.2` verifier) plugs into: the `source` column already distinguishes agent-authored skills, so `SKILL-4` becomes a policy about which drafts auto-promote, not new machinery.
  - **Progressive disclosure, and why it is an `@agent.instructions` block rather than a corpus source.** Level one is every published skill's name and description, injected fresh each turn (`_skill_catalog` in `agent/engine.py`, beside `_document_state`) under a character budget — `SKILL-2` says relevant skills are surfaced *automatically*, and a tool the model has to think to call is not that. Level two is `skills_open`, returning the full `SKILL.md`, paid for only when a skill is actually relevant. Level three is the bundle's own files. Enrolling skills as a corpus `SourceAdapter` was rejected on two grounds: a skill is guidance to *apply*, not knowledge to *retrieve*, so it would double-surface against the injected catalog; and corpus retrieval has no notion of `published`, so a draft could leak into context through the back door. **Known limit:** the budget drops the oldest entries with an "…and N more" tail, so a large library silently loses its tail from the prompt — publishing a skill can evict another with no signal. Ranking descriptions by retrieval is the noted scaling seam; the directory screen showing what currently fits is the v1 mitigation.
  - **Bundled scripts run in the sandbox, and only there.** `skills_open` stages the whole bundle to `/work/skills/{name}/` through `SandboxSession.write_file` — the same host-side bind-mount path `attachments_provision` already uses — so reference files are real files and scripts are ordinary sandboxed code run through `code_execute`. Nothing about a skill creates a host path: it inherits `XC-SEC-7`/D23 unchanged, and a skill that wants the host has to ask for `run_host_command` like anything else, with its explanation and its approval. Re-staging is a byte-compare, so re-opening a skill in a warm session is a no-op. Staged files carry no exec bit, so the tool's contract tells the model to invoke scripts explicitly (`python …`, `bash …`) — a small honesty about the mechanism instead of a `chmod` the sandbox seal wouldn't preserve anyway.
  - **`allowed-tools` is recorded and displayed, never enforced.** The standard's field is a per-turn tool grant in Claude Code; enforcing it here would mean removing tools from the catalog mid-turn, which contradicts `AE-4.2` ("every permitted tool available the whole turn") and D3's no-runtime-relevance-filter stance. So it is parsed, persisted, surfaced in the editor and in `skills_open`'s result labeled *advisory*, and it grants nothing and restricts nothing — the model may self-limit, and the operator can see what the author expected. The revisit trigger is explicit: if `AE-4.2` is ever relaxed, this becomes a real restriction rather than a note.
  - **A published skill is not untrusted content.** Web pages, corpus hits, and chat attachments are `wrap_untrusted`-fenced (`XC-SEC-5`) because they arrive from outside the operator's intent. A published skill arrived *through* it — the operator read the bundle and pressed publish — so fencing it as data would be theater, and would fight the whole point of a skill, which is that the model follows it. The publish gate is the control; the fence would be a second, weaker one.
  - **`name` is cleartext, and that is a genuinely weaker posture than the rest.** Description, body, files, and preserved frontmatter are all AEAD-sealed. `name` cannot be: it is simultaneously the uniqueness key, the bundle's directory name, and the handle the model calls the skill by. So anyone holding the database file learns the *topics* of the operator's skills, if not their contents — consistent with `Upload.mime` and `Document.doc_type` staying clear (D17), but worth naming rather than burying, since a skill's name is more revealing than a MIME type. A staged bundle is also re-sealed a second time inside the sandbox workspace tar on idle-reap; harmless, bounded by the 30 MB cap.

- **D33 — Harness lifecycle registry 🟢 DECIDED: one owner for background start/stop order; teardown position implied by setup position.** The refactor's first move (core-harness-and-plugins reorganization). The app lifespan had grown two hand-maintained mirrors of the same sequence: every capability's `.start()` at its construction point, and a `finally` block replaying the whole thing in a bespoke stop order — 21 modules' background work (write-behind drainers, sync loops, container monitors, fire-and-forget startup tasks, clients needing closing) each wired twice, in the right position, by hand. - **D37 — Mid-run message steering (`CHAT-8`) 🟢 DECIDED: an inbox on the `Run`, drained at model-request boundaries; the busy 409 becomes queue-into-the-live-run; injected messages split back out at persist.** The composer was hard-locked while a run streamed — a second `POST /chat` on a busy conversation 409'd — so a mid-thought follow-up ("also check X") had to wait out the whole turn. The fix keeps the one-live-run-per-conversation invariant and adds a queue in front of it, never a second concurrent run.
  - **The inbox lives on the `Run`** (`pending_messages`, beside `parked_payload`): in-memory, synchronous `enqueue/edit/withdraw/drain` (race-free under single-threaded asyncio — no `await` between check and mutate anywhere on the path), surviving park/resume because the same `Run` object does. Four additive v1 events (`message.queued` and `message.edited` with the text inline, `message.withdrawn`, `message.injected`) make queue state fully reconstructable from SSE replay, so a reattaching client rebuilds pending bubbles with no extra endpoint.
  - **The API is conversation-scoped so the client never picks a path.** `POST /chat` on a busy conversation now enqueues into the live chat run (returning the same `run_id` + a `queued_message_id`) instead of 409ing; if the run went terminal a beat earlier the claim simply succeeds and a normal run starts. The 409 survives only where queueing is genuinely impossible: a regenerate/edit holds the claim, the run isn't a chat turn, or the send carries attachments (steering is text-only v1 — a file can't ride an existing run's request). Withdraw is `DELETE /runs/{id}/messages/{message_id}` and edit-in-place is `PATCH` on the same path (full replacement text; the message keeps its id and queue position), both 404 for a message the run has already consumed — a withdrawn/edited-too-late race resolves loudly, never silently.
  - **Two injection sites, both draining in order, neither interrupting an in-flight stream.** Mid-turn: `stream_agent_run` hands each yielded-but-not-yet-run `ModelRequestNode` to the engine, which appends one `UserPromptPart` per queued message onto the pending request — the same merged shape the library itself produces (`CallToolsNode.user_prompt`), and the approval-resume path inherits it for free. End-of-turn: when the model finishes with messages still queued, `_drive_turn` continues the same run with the queued texts as trailing user requests (`prompt=None` — the regenerate continuation shape), sharing the turn's usage/loop budget so a steady drip of messages can't extend the bounds.
  - **Split at persist.** The live request that carried tool returns + injected user parts is persisted as separate `ModelRequest` nodes (tool returns, then one per message), so every steered message is an ordinary user node in the branch tree — its own bubble, its own edit/regenerate anchor — while replay stays wire-identical because the library re-merges consecutive requests at wire-prep. Same accepted live-vs-persisted divergence class as the verifier's `clean_drop` and attachment capping.
  - **Nothing queued is ever silently lost.** A message still in the inbox at terminal (cancel/error/timeout — the normal end-of-turn path consumes its queue) is dropped server-side but visible in replay as queued-never-injected; the frontend removes the pending bubble and restores the text to the composer. The frontend keeps the composer live while streaming (SEND beside STOP), renders queued bubbles with a WITHDRAW affordance, and splits the assistant flow at each `message.injected` so the live transcript matches what a reload projects.

- **D38 addendum — the `for_run()` reason was imprecise; the call was right.** D38 says a toolset registration "never reaches `for_run()`". That is not what the installed library does: `AbstractToolset.for_run(ctx)` *is* called once per run (`pydantic_ai/agent/__init__.py:1624`, `:3348`) and propagates through `CombinedToolset` and every wrapper, so the `Prefixed → Combined → filtered` stack passes it through with `RunDeps` already on `ctx.deps`. A category object is built once for the whole app, so anything that must differ *per conversation* — a workspace root, a plan store, a sub-agent's root — still needs the rebinding wrapper `tools/files.py` established. Worth recording because the mistaken reason suggests a fix (`for_run`) that compiles, passes an isolation test, and leaves both threads pointed at the wrong tree.

- **D39 — Fork a conversation from a message 🟢 DECIDED: a copy into a new thread, not a fifth move within the tree.** The store already had three ways to branch — `regenerate_point`, `edit_point`, `rewind` — and all three move the **active leaf** inside one conversation's tree. A fork is the thing none of them is: history up to a chosen turn, in an *independent* conversation, with the original untouched. Adding it as a fourth leaf move would have been wrong in the one way that matters — the operator's original thread would change.
  - **Mechanism.** Walk the active path to the tail of the chosen turn (the same "tail of *this* turn" rule `rewind` uses, so forking an assistant turn carries its tool exchanges rather than cutting the turn in half), deep-copy each node with a fresh id and re-based parent, and drain through the normal write-behind path so the copy is sealed on write like everything else.
  - **What it does not copy is the interesting part.** Runs and pins belong to the turn and the thread that held them. A compaction checkpoint keeps its summary (real history) but drops `compacted_through`, which names a node id in the source tree — carrying it would leave a dangling reference `model_history` walks into. The workspace's *contents* are not copied either: a replayed transcript can already name paths a recycled sandbox no longer has, and `attachments_provision` is the existing way back.
  - **A coding fork branches from the source's branch, not the project's base ref.** The copied transcript describes files as they are on the source conversation's branch; branching the fork from `base_ref` — what a first coding turn would otherwise do — hands it a tree that contradicts its own history, which is exactly what forking is supposed to preserve. Best-effort: a source that never cut a branch leaves the fork to cut its own normally.
  - **The route returns the fork, not the source**, so the client navigates in one round-trip; the source is claimed for the duration of the walk, since a run appending to it mid-copy would produce a fork of a history that never existed.

- **D40 — Projects, and one scope rule for lists and recall 🟢 DECIDED: `visible = unfiled ∪ active`; isolation by column, not by a second store.** A project is a directory the operator works in, and the app filters by it. The only genuinely dangerous decision here is what "filtered" means.
  - **Unfiled is global; a project *adds*; another project is never visible.** An earlier draft made lists a hard filter (`project_id = active`) and recall a union, which is two rules — and it produces a cliff: activating the first project would make the operator's entire pre-existing history, every row with `project_id IS NULL`, vanish from RECENTS, Documents, Tasks and Research at once. Unfiled-is-global makes activation purely **additive**, which is what makes the migration safe (every existing row is unfiled) and what lets a project chat still reach everything the operator has ever learned.
  - **`project_clause`, not `column.in_(visible)`.** SQL `IN` never matches NULL, so the obvious spelling silently drops every unfiled row. A query written that way looks correct, passes a test that only uses filed rows, and blanks the operator's history in production. One helper holds the rule; every scoped query calls it.
  - **The scope is resolved once, at the request edge.** `X-Ody-Project` (set in the single `authHeaders()` choke point; the literal `all` means unscoped) falls back to the stored active project, and `routes/deps.project_scope` returns the *visible set* rather than the active id so no route re-derives "unfiled plus this one" and eventually gets it wrong. Deliberate asymmetry: a **tool** never reads it. `RunDeps.project_id` comes from the conversation, because switching the active project must not change what an already-running thread is doing.
  - **Isolation is a `WHERE` clause, not a second database.** The corpus already keys every hit on a globally-unique `source_id` and already filters in SQL (`kb_excluded` proves the pattern). A per-project store would fork the retrieval path, break RRF fusion across the union above, and duplicate the sealing/embedding lifecycle — all to enforce a clause. Pinned by a test that a second project's chunks are unreachable from the first.
  - **No corpus source is created for a project's code.** Chunk-and-embed is a poor retrieval strategy for source: it dissolves the structure (imports, call sites, definitions) that makes code findable and returns plausible neighbours rather than the definition asked for. What a project *does* file into the corpus is its prose. The tools that actually work on a codebase are the ones coding mode already gives — `rg` through the shell, the file tools' own search, and the read-only explorer sub-agent. If code indexing is ever wanted, one `CorpusSource` per project through the existing `FolderAdapter` needs no new storage.
  - **The scheduler's tick is deliberately unfiltered** — it runs everyone's due tasks regardless of what the operator is looking at, and scoping it would silently stop automation.

- **D41 — Coding mode on git worktrees 🟢 DECIDED: one workspace resolver, one worktree per project, and the operator's tree written only by a merge they press.** The agent should work in a real project directory on the host. The safety question is not "can it write files" — it is *which* files, and what the operator has to do to accept them.
  - **The worktree is the boundary.** A coding conversation gets a branch (`ody/<conversation-id>`) checked out in a worktree beside the repository. The agent edits and runs tests there; the only thing that ever touches the operator's own checkout is an explicit merge. Deleting a thread with unmerged commits is refused unless the caller says to discard — merging is a deliberate act, so destroying has to be at least as deliberate, or deleting the thread becomes the quiet way to lose exactly what the merge gate protects.
  - **One worktree per *project*, not per conversation.** A worktree is a full checkout, so per-conversation means a fresh `node_modules` / `.venv` / build cache for every thread — minutes of reinstall before the agent does anything useful, and no reap policy short of deleting the thread. Sharing one keeps those caches warm, which is most of the reason to code on the host at all. The cost is that only one coding conversation can hold a project at a time, and that is **enforced** rather than allowed to silently interleave two threads over one checkout.
  - **Worktrees live outside `data_dir`.** An approved host command is fenced by `services/sandbox/host.py`, which denies reads of the whole data directory; a worktree beneath it would be unreadable by the very shell that has to build and test in it. So a worktree is plaintext on disk — a deliberate, narrow exception to at-rest encryption, and not a new exposure: it is a checkout of the operator's own already-plaintext repository.
  - **`git init` is never implicit.** Creating a repository in someone's directory and committing its whole contents is a real, visible side effect. It happens through a route the Projects UI calls after asking; the agent has no path to it.
  - **The load-bearing piece is the workspace resolver, not the shell.** Four subsystems assumed the workspace *was* the container sandbox — the file tools, `code_execute`, attachment staging, the skills bundler — and `tools/files.py` stated the invariant that held them together: *these tools reach exactly what `code_execute` reaches and nothing else*. Re-rooting only the file tools breaks that **silently**: the agent edits a file it cannot run, attachments land where its file tools can't see them, an opened skill's scripts point at a container that isn't in play. So `services/workspace.py` answers *where this run's file work happens and how a path in it is named to the model* — those differ in chat mode (`/work/...` across the bind mount) and coincide in coding mode — and all four route through it. That is what makes coding mode a mode rather than a fifth special case.
  - **Mode is a per-run tool filter, not a second catalog.** Assembling a different category map per mode would let the settings page and the agent's real stack disagree, which is the exact failure the namespacing exists to prevent. `shell` and `repo` register like every other category and are withheld from a chat run by a third source unioned into `effective_disabled_tools`, beside the operator's own set and offline's. The literal name set is checked against the real catalog by a test, because a renamed tool would otherwise stop being filtered and read as "coding tools now available in chat".
  - **What this gives up, stated plainly.** `Shell` spawns processes itself, so unlike `code_run_host_command` there is **no OS-level fence outside the worktree**: an allowlisted `python`, `make` or `uv` can spawn anything the operator can. What remains is the worktree and its throwaway branch (which is what protects the operator's actual work — the thing asked for), approval on the first command of a conversation (grantable for the thread), `denied_env_patterns` keeping model API keys out of every spawned environment, the harness's destructive-command denylist (its own README calls it a guardrail, not a security boundary), and coding mode being chosen explicitly for a thread bound to a named project. `code_run_host_command` keeps its fence unchanged — this adds a second, more permissive path rather than loosening the existing one.
  - **An allowlist was considered instead of the approval gate, and rejected.** A coding agent needs whatever build tool the project uses, so any allowlist honest enough to be useful is long enough to be meaningless — and still bypassable through an allowed interpreter. One deliberate "yes, run commands in this project" is a stronger statement and a far smaller nuisance. If the fence turns out to matter more than toolchain fidelity, the fallback is to bind-mount the worktree into the container sandbox, which trades away the operator's real `python`/`uv`/`node` — usually the whole point of coding on the host.
  - **The chassis commits, because nothing else does.** The agent has file and shell tools and no `git commit` — deliberately: when a body of work becomes a commit is not a judgement to hand the model. The first cut of this feature simply forgot to close that loop, and the result is worth recording because it *looked* correct from every angle: `diff` compares two refs, so a session that rewrote ten files reported "0 files, +0 −0", MERGE landed nothing, and the delete gate never fired — deleting the thread silently threw the work away. Every test passed, because every test committed by hand first. So `snapshot` stages and commits onto the conversation's branch, and `diff`/`merge` call it before they read; the tests now edit and **do not** commit, which is the state every real session is in.
  - **A merge refuses when the operator's checkout is on another branch**, because `git merge` lands on whatever HEAD is and the diff they reviewed was computed against the project's base ref — merging elsewhere would give them a different result from the one they read. It also **releases the project**, or the holder map keeps it locked to its first coding thread forever and the busy message names an escape ("finish or merge that one first") that cannot work.
  - **Deleting a project unfiles its rows rather than orphaning them.** `visible = unfiled ∪ active` and a deleted id can never be active again, so rows still pointing at it would vanish from every listing permanently. The operator deleted a *label*.
  - **Naming: not `CodeMode`.** The harness ships a capability literally called `CodeMode`; it is unrelated — a context-saving technique where the model writes one script that calls many tools. Ours is a mode of the *chat*, named `coding` in the wire contract and the UI.
  - **Harness capabilities deliberately not adopted:** `ClearToolResults` / `WarnNearLimits` / `ToolOutputLimits` (this codebase has exactly one context reduction — conversation compaction, on measured pressure — and taking `Coder` whole would quietly reinstate the tool-result digesting that was removed by name); `ToolApproval` / `HandleDeferredToolCalls` (the approval gate is already built on Pydantic AI's deferred-tool mechanism directly); `Researcher` (this product has its own pipeline); `Memory`, `ConversationSearch`, `Skills`, `WebSearch`, `WebFetch` (all already built against local, encrypted stores a generic capability would bypass); `ModalSandbox` (cloud). `Guardrails`, `PromptInjectionDefender` and `SpendLimits` are genuinely interesting and genuinely out of scope.

- **D42 — Research and delegation as agent tools 🟢 DECIDED: an abstract launcher in `services/`, and one coarse `delegate_task` rebound per conversation.** Deep research was fully built but reachable only over HTTP — `research_launch.start()` took a FastAPI `Request` and pulled handles off `routes/deps.py`, so a tool could not reach it without inverting the layer order.
  - **The launcher is an ABC in `services/`, implemented in `research/`.** `tools/` sits below `research/`, so the tool resolves `ResearchLauncher` from the capability bag and the pipeline registers its implementation through a new manifest capability form (`(instance, as_type)`), which lets a feature export a concrete object *under an abstract key*. No layer inverts and no tool imports a pipeline.

Approval-gated, because it spends real tokens and hits the open web unattended — and the `question` surfaces on the prompt, so the operator sees what will be researched.
  - **Delegation is one coarse tool, not a catalog.** `SubAgents`' `delegate_task(agent_name, task)` is the right grain: many narrow tools cost the model accuracy, and a single parameterised delegate keeps the whole capability to one catalog entry the operator can switch off. Registered as a toolset for the same reason D38 gave for `Planning`, with the delegate listing re-delivered through the `InstructionProvider` seam.
  - **Rebound per conversation, and the reason is rooting rather than isolation.** `SubAgentToolset` defines no `for_run`, so the library hands every run the same instance — and that instance is where the sub-agent's workspace root and the event-stream handler live. A shared one would let a sub-agent read another conversation's workspace and stream its progress onto a dead run. A test asserting only "two runs don't share mutable state" would pass with both rooted at the same directory, which is precisely the bug — so the assertion is that the **roots differ and match their own conversations**.
  - **Sub-agent work is streamed** onto the parent's existing `tool.progress` frame, flattened to one short line per event because `partial` is a string. Without it a delegation is a multi-minute silent gap in the transcript. The frozen event protocol is untouched.
  - **`inherit_tools=False`**, which also excludes the delegate tool itself, so a sub-agent cannot recurse into further delegation.

- **D43 — Portalled, collision-aware popovers 🟢 DECIDED: measure and place at open, in a body portal.** `Popover` anchored its panel with pure CSS — a `relative` root and an `absolute top-full` panel — so a menu near the viewport bottom overflowed, and, worse, the chat transcript's `overflow-y-auto` container **clipped** it outright. No amount of `align` tuning fixes a clip.
  - **Mechanism.** The panel renders through a `<Portal>` to `document.body` with `position: fixed`, so no ancestor's `overflow` can clip it; on open both trigger and panel are measured and placed — flip above when there is more room there, shift horizontally to stay inside an 8px margin — and recomputed on capture-phase `scroll` (so scroll containers fire) and `resize`.
  - **The height clamp is conditional**, which is the subtle half: an unconditional inline `max-height` would silently override every caller's own `max-h-*` (Combobox's `max-h-80`, Select's `max-h-72`) and change how those menus scroll. The clamp — and the `overflow-y-auto` that goes with it — applies only when the panel genuinely does not fit.
  - **The placement maths is pure and unit-tested** (`popoverPlacement.ts`), including mutation checks that the flip and the clamp fail when broken. Fixing it in `Popover` means every `Menu` / `Select` / `Combobox` in the app inherits the fix.

- **D44 — One models page 🟢 DECIDED: `/settings/models` absorbs LOCAL MODELS.** Local-versus-external was never a distinction the operator makes — a model is a model, and which host runs it is one column. Keeping them apart meant configuring "which model answers me" on one page and "which models exist" on two, which is the same confusion the three role cards were introduced to end.
  - **The serving controls stay in `features/cookbook`** rather than moving into `features/settings`: the Cookbook's other tabs (embedding, compare, get-started) drive the same lifecycle, so moving them would leave cookbook importing from settings — the same cross-feature import, inverted, plus a large mechanical churn. The Models page renders them; it does not own a second copy.
  - `/models/cookbook/local` becomes a redirect, so an existing bookmark or an older transcript's link still lands somewhere useful.

- **D45 — Local model serving 🔴 REVERSED: the platform works off endpoints.** Odysseus owned the full local-serving lifecycle — download weights from HuggingFace, install and supervise an inference engine (llama.cpp as the universal baseline, MLX on Apple Silicon), register the resulting process as a loopback endpoint, reconcile orphans across restarts, and detect host hardware to recommend a fit. That is roughly 7,000 lines across both layers, and it is gone. **Every model is now reached through an endpoint** — an OpenAI-compatible URL the operator points at, whether that is a server on their own machine or a lab's API — and what a model runs on is decided where it runs.
  - **What reversed the call was ownership, not capability.** Serving worked. But an inference engine is a fast-moving subsystem with its own release cadence, its own quantisation formats, its own flag vocabulary per version, and its own failure modes on every host — and owning it means tracking all of that forever in order to be a slightly nicer front-end for a `serve` command the operator can run themselves. The registry, the role bindings and the fallback chains are the part that is genuinely ours, and they work identically against a process someone else started.
  - **This supersedes the `local` provider adapter and its schema** (D36): `managed` and `live_status` on the endpoint described process liveness of a thing we no longer run, so both columns are dropped and an endpoint is once again just an address with credentials and capabilities. It also retires the hardware-fit half of D26's resource governor, and D44's "the serving controls stay in `features/cookbook`" — there are no serving controls.
  - **Keeping MLX management was the alternative considered**, on the argument that first-class Apple Silicon serving is much of the reason to self-host on the operator's own hardware. It was rejected on the same ownership ground: MLX alone is still an engine lifecycle to track, and a product that manages one engine but not the others is harder to explain than one that manages none. An operator who wants MLX runs `mlx_lm.server` and points an endpoint at it — one line of setup, and it is theirs to upgrade.
  - **Three things had to be lifted out before the deletion**, or they would have gone by association. The **embedding reindexer** and its backfill lived in the serving manifest, because binding a freshly served embedding model is what most often triggers a heal; that manifest is split rather than deleted, and the reindexer keeps its ordering. The **host file picker** was mounted under `/models/serving/file-picker` and is not about models at all — it is how any field wanting an absolute host path gets one, so it moves to `/host/file-picker` beside the Projects feature that is its remaining caller. **Compare** was a Cookbook tab and is now its own page: it depends on the registry and the chat stream, and on nothing that went.
  - **What survives untouched**: endpoint CRUD and probing, the `main`/`utility`/`embedding` role bindings, `resolve_background`'s degrade-onto-`main`, the ordered fallback chains, embedding reindex and recall health, and `/overview` capability health.

- **D46 — Configuration as one dialog, and the rail as chat 🟢 DECIDED: six categories in a framed overlay; the rail is the thread list.** The nav rail listed nineteen surfaces across six areas behind a switcher. That hierarchy was itself a fix — a flat nineteen had none — but it treated the rail as the app's table of contents, permanently occupying the space beside the work, and gave a standing row to every value an operator sets twice a year.
  - **The split is what you *go to* versus what you *set*.** A destination has a screen you work in: chat, the knowledge base, research, MCP, the compare bench, and mail/calendar/tasks. Everything else — appearance, chat defaults, offline, tools, search providers, projects, skills, memory, models, the vault, both token surfaces, integrations, backup, health — is configuration, and configuration is something you open deliberately and then leave. An overlay says that; a nav row says the opposite.
  - **The dialog's state is the URL** (`?settings=<category>`), so it is bookmarkable, back-button-able, and opens over wherever the operator was. Opening pushes a history entry and switching category replaces one: closing should be one press, and browsing six categories should not be six.
  - **Every retired path forwards rather than 404s.** A settings page's URL is exactly the kind of thing that sits in a bookmark or an old toast, so the map from retired path to category is explicit and the not-found route consults it first. A forwarding path also has to read as *connected*, or the shell's NOT CONNECTED banner flashes over the redirect.

Worth recording because that flag going quietly unread is exactly how a mock surface starts looking real.
  - **The container is `ConstructionReveal`, shared with the View and the palette**, through a new `FramedOverlay`. It could not be built on the existing `Modal`: that component's backdrop is the *ancestor* of its dialog, and `backdrop-filter` blurs only what is painted inside its backdrop root — which any ancestor with `opacity < 1` creates, including a fading backdrop. Nested that way the glass blurs nothing while its fill still tints, so the failure looks like a slightly lighter panel rather than like anything broken. The backdrop is a sibling.

- **D47 — The document editor, gallery, host shell and code runner 🔴 REMOVED.** Four surfaces left the product outright. They were built, they worked, and none of them was the thing this workspace is for.
  - **Documents took the agent's authoring tools with it**, which is the part worth stating plainly: `document_create` / `document_edit` / `document_suggest` are gone, along with the suggestion-review pipeline, the versions and keeper flags, the `document.created`/`delta`/`committed` events, and the View's document tab. The assistant answers in chat; documents are written where documents are written. Removing the human-facing pages while keeping the agent tools was the obvious middle option and was rejected as the worst of both: a body of authored work with no page to manage it on.
  - **The unsaved-edit guard went with them.** The View's deferred-navigation bar, `viewerDirty`, and the scroll-to-first-change anchor existed solely to protect an inline document edit. A guard over nothing is worse than no guard: it looks like the feature still has an edit path.
  - **The gallery's albums are gone; attachments are not.** Chat still uploads, thumbnails still render from `/uploads/{id}/thumbnail`, and the Lightbox still opens them. The uploads *page* went too — the files are only ever relevant inside the conversation that produced them — while the uploads *seam* stayed, because deleting it took the composer's attachments with it.
  - **The shell and the code runner were the two "run something" surfaces, and neither was the agent's.** The operator's PTY is a terminal emulator competing with the terminal they already have; the in-browser runner was 13 MB of vendored Pyodide for a scratchpad. **The agent's own `shell` toolset and its approval-gated `code_execute` are untouched** — those are capabilities the assistant reasons with, not screens, and they are the reason the sandbox stays.

- **D48 — An unbound `main` 🟢 DECIDED: resolve a default, report it, never write it.** A workspace with endpoints but no `main` binding refused every turn, while the composer's picker displayed a model anyway — it resolved a *display* fallback of its own ("first discovered choice"). So the operator saw a model, SEND refused it, and re-picking that exact model in the dropdown was the only way to make the two agree. The display was a fiction: nothing had been bound, and the send path deliberately sends no override.
  - **One answer, not two.** `main` with nothing bound now resolves to the first usable endpoint and model, and `GET /models/roles` reports what it resolved to with `implicit` set. The picker shows *that* rather than guessing, so what is displayed and what runs come from the same place. The frontend's fallback is deleted — it existed only to paper over the gap this closes.
  - **A default, never a pin.** It is recomputed, never stored. Writing it would fasten `main` to whichever endpoint happened to exist first, so adding a better one later would silently keep the old choice — and the operator would never have made it. This is the shape `utility` already had: degrading onto `main` is spelled as the state the workspace is in, not as a fourth thing to configure.
  - **The `implicit` flag is what makes showing it safe.** The picker treats a default and a pin identically, because what a turn runs on is one fact however it was arrived at. The Models card does not: it describes the *configuration*, so it says "defaulting to this", since a default moves and a pin does not.
  - **Scan order is the catalog's, not insertion order** (`list_endpoints` sorts by name), so the same set of endpoints always yields the same default. Disabled endpoints are skipped. The model is the endpoint's configured default when it has one, else the provider's first discovered model — a rule reading only the column would find nothing in exactly this workspace's shape, one server serving many models with none written on the row.
  - **Memoized per owner, invalidated explicitly** on endpoint create/update/delete. Deliberately *not* folded into `forget_context_windows`, which `list_provider_models` also calls — and that runs *inside* the implicit scan, so sharing the invalidation would leave the scan's own result depending on whether the assignment happened to come after the clear.
  - **An empty workspace is still degraded.** The default fills a vacuum where something usable exists; it does not invent one. The send gate keeps firing, and "add an endpoint" keeps its own surfacing rather than being talked over by "your endpoint reports no context window".

- **D49 — The context gauge before the first turn 🟢 DECIDED: a gauge with nothing to measure says nothing.** The ring was mounted unconditionally and painted an alert-toned track reading "context window unknown" whenever it had no usage — which on a new thread is simply *before the first response*. A fresh chat therefore opened on a red gauge announcing a fault nobody had established.
  - It is now mounted only once a run has reported usage. The genuinely-unknown window is not lost: it is the send gate's, which blocks SEND and explains what to set and where — a stop the operator can act on, rather than a colour on a dial.
  - The unconditional mount had a stated reason — that vanishing would leave the operator guessing whether the gauge or the setting was missing. That reasoning holds only when the absence is ambiguous, and it is not: before the first turn there is nothing to measure, and after it the ring is always there.

- **D50 — The auth gate 🟢 DECIDED: a render branch, not a route.** Logging in never painted the app. The operator typed the password, the form stayed on screen, and only a manual browser refresh got them in — every single time.
  - **The cause was that login was a *route*.** The gate redirected an un-unlocked workspace to `/login`, so unlocking meant navigating back, and the router wraps a navigation in Solid's `startTransition`. A transition commits only once every resource read in the new tree has settled, and it shows no fallback while it waits: the old UI stays. The app shell's cold `/projects` and `/conversations` reads — both outside the shell's own Suspense boundary — therefore pinned the transition on the login screen. A reload "fixed" it because there is no transition on a cold render; the same pending resources simply suspend against a fallback.
  - **So the gate renders the auth screens itself.** Unlocking is now a signal flip inside one already-mounted route: the subtree swaps in the same tick and the shell's resources suspend normally. `/login` and `/signup` survive as redirects to `/` — bookmarks and old toasts point at them — and that redirect is safe precisely because the tree it commits to reads nothing.
  - **`window.location.assign("/")` after login was the obvious two-line alternative**, and it is what the operator was doing by hand. Rejected: it is a full SPA reboot with a white flash on every login, and it leaves the pin in place for the next navigation into a cold tree rather than removing the cause. Making the shell's resources non-suspending was rejected too — one future `<Resource>` in the rail brings the whole failure back, silently.
  - **The Suspense boundaries got fallbacks as part of the fix**, root and content region. A boundary with no fallback renders a blank frame, which is how a slow first paint reads as a broken one.

- **D51 — What says a workspace exists 🟢 DECIDED: the keyfile *and* its database.** Deleting `data/app.db` did not reset anything. `Vault.is_initialized` is `keyfile.json exists`, and the keyfile sits beside the database rather than inside it — so a cleared database still answered "initialized", `/setup` still returned 409, and the operator was asked to unlock a key that now protected an empty workspace.
  - **The database's survival is sampled once at boot**, before the schema is created, because afterwards a deleted database is indistinguishable from a fresh one. `/auth/status` reports the disagreement as `db_missing`, and `/setup` clears it — the workspace it just created *is* in this database.
  - **It is not a new session state.** The workspace is still locked, and unlocking with the existing password still works and still lands somewhere usable. What changed is what the operator should be *told*, which is a different axis from what they can *do*, so both readings stay on offer: carry on in an empty workspace, or start fresh.
  - **`POST /setup/reset` is guarded by state, not credentials** — the same posture `/setup` has, and for the same reason: there is nobody to authenticate to yet. What makes that safe is that the state it demands cannot describe a live workspace. A workspace in use has a database that predates the boot; an unlocked vault means the caller is already inside.
  - **The wipe is an exclusion list, not an inclusion list.** Everything under `data/` is runtime state the app wrote for itself, so the reset removes all of it bar the open database handle and the SearXNG bind mount. A sealed directory added next month is then caught by default instead of surviving a reset and outliving the only key that could read it. The confirmation names what goes, because "this cannot be undone" does not tell an operator that their uploads, corpus and View snapshots are inside "this" — and a typed `RESET` stands between the click and the loss.

- **D52 — The context breakdown 🟢 DECIDED: measure it itemised, emit only what weighs something.** The gauge split the window three ways — brief, tool schemas, conversation — and that is where the reading stopped and the operator's actual decision started. "Tools are 40% of your window" is not a thing anyone can act on; "`external` is 40%, across 68 tools" is a switch to go and find.
  - **The itemisation is captured where it exists, which is not where the total is.** Tool schemas group by the namespace prefix every tool is already registered under, so the readout's rows are the same rows as the tool settings page — the split is only useful if there is one switch per row. The standing brief cannot be split the same way: the library concatenates every instruction provider into one string, and by the time a request exists there is no seam to cut on. So each provider is wrapped and its own return measured as it runs, with the fixed prompt taken as the remainder — which keeps the blocks summing to the brief that was actually sent even when a provider goes unmeasured.
  - **A row exists because it weighs something, never because it could.** No fixed roster, no zeros: a thread that has called no tools has no tool-results row, a catalog with no MCP servers has no row for them, and each appears the moment it starts costing the window. A roster with zeros is a form to read; a list of what is actually there is something to scan. Anything that rounds away to nothing is dropped from the rows and kept in its group's total, so the sums still hold.
  - **Two resolutions, one measurement.** The three totals stay and are now the sums of their own segments, so the bar and the rows cannot disagree. Segments are empty when the detail could not be measured — an overhead cached before this existed, a library change that moved an internal — and the coarse reading survives on its own.
  - **~~Persisting the itemisation was rejected for the reason the totals aren't persisted either.~~** Overhead is configuration, not history: it describes what the *next* turn will cost, so a stored copy would confidently report the old tool weight to a thread opened after half the tools were switched off. It stays a process-local per-mode memory, absent until some turn has run. **Reversed by D54 — the reasoning didn't survive contact with what the panel actually shows.**
  - **Two counting bugs surfaced while splitting.** The system prompt was counted twice — once as the brief, once as a message part — and tool-call arguments were counted not at all. Both were invisible in a three-way split that scales to the provider's total: the error just moved silently between the parts.
  - **The panel folds the detail behind the group.** A dozen rows at rest is a panel to study rather than glance at, so the three groups plus free space are the resting state and each opens onto its own rows. Free space is a row of its own because the question a *window* gauge is opened to answer is not what is in there but how much room is left.

- **D53 — Parallel tool calling 🟢 DECIDED: on by default, for every endpoint.** The agent called tools one at a time, and nothing had decided that: the chat agent was built with no `ModelSettings` at all, and the standing brief said "reach for your tools" without ever saying *several at once*. Three independent searches therefore cost three model round-trips and three of the run's twenty-five steps, and the work the operator watches — search especially — read as a queue rather than a step.
  - **The wire flag is the permission; the prompt is the behaviour.** `parallel_tool_calls` only says the model *may* batch. What makes it batch is two sentences in `INSTRUCTIONS`, which is also where they belong: an operating rule re-asserted fresh every turn rather than anchored once in a history that can be reconstructed around it.
  - **A flat default beats a capability seam here.** Both model classes that read the field omit it from a request carrying no tools, so a toolless utility call is untouched and no server is handed an argument for a request with nothing to parallelize. A per-endpoint `parallel_tools` column beside `native_tools`/`vision`/`thinking` was rejected on that: a migration and a switch for a field the library already withholds when it cannot apply. A per-provider method mirroring `reasoning_off` was rejected too — reasoning-off is genuinely model-shaped, this is not.
  - **Declared at agent construction, not per run.** A park for approval stashes the agent object itself on the `ParkedTurn`, so settings baked in at construction are inherited by every resume with nothing threaded through the payload and nothing missing from one written before the setting existed. `agent.iter(model_settings=…)` would have needed both.
  - **The backend was already batch-ready; the transcript was not.** The library runs a batch concurrently, the node stream was already timed as a batch, every event is keyed by its own `tool_call_id`, a park already covers N pending calls, and the loop guard keys on `(name, args)` so distinct concurrent calls do not read as a repeat. The chat UI was the part that assumed one call at a time — three running tools are three groups, which is exactly the run length the work log folds away, so the common case of parallel calling would have hidden its own spinners. Work in flight now blocks the fold, the progress rail counts live calls instead of naming the last one, and every group with a call out reads as live.
  - **Research is wired at the seam and inert there today.** Its agents are structured-output calls with no toolset and the rounds search in code, so the setting changes nothing now. It is set anyway, at the one place that feeds all of them, so the default stays uniform and an agent that later grows a toolset is not the one that missed out.

- **D54 — The context breakdown on a cold load 🟢 DECIDED: store the overhead on the conversation, one per thread, last turn wins.** Reopening a thread showed a single undifferentiated "In use" row where an active one showed the itemised split. The breakdown was rebuilt from a process-local `OverheadCache` keyed by conversation *mode*, so it survived only until the next backend restart — and the operator's workaround was to send a message, which is the opposite of the decision the panel exists to inform (whether to send one at all).
  - **D52's reason for not persisting was wrong about which number this is.** "Overhead is configuration, not history — it describes what the *next* turn will cost." But the figure being split is `context_footprint`: the **last response's** prompt plus generation. That is history, and it is already stale in exactly the same way if the operator toggles tools off. The panel's real claim is "the last turn cost 47K tokens, and here is what they were", so splitting it by whatever configuration a process cache happens to hold is the incoherent half. The overhead measured *on that same request* is strictly more accurate, not less.
  - **The mode key was quietly wrong too.** Keyed by mode and nothing else, a coding thread bound to project A could render project B's instruction blocks and B's enabled-tool weights. Even when the cache was warm, the split was not guaranteed to describe the conversation being looked at. Keying by the conversation removes that failure entirely rather than narrowing it.
  - **Per conversation, not per response.** The message row was the tempting home — it is where `llm_ms`/`ttft_ms`/`tool_ms` live, and it would follow a rewind or a version switch exactly, since the split would be read off whichever node is currently last on the active path. It was rejected on storage: `record()` writes one row per `ModelResponse`, so an agentic turn of eight steps is eight rows, each carrying a ~700–900 byte blob that is *identical* to its neighbours (the same agent, the same toolset, re-measured per request). A long thread would accumulate hundreds of near-duplicate copies to serve one figure that is read once, on open.
  - **What that trades away is bounded, and it is proportions only.** Rewind to an older turn and the newest turn's overhead splits that older turn's footprint. The total stays the provider's own number — every piece is scaled to it — so the error can only redistribute the bar, and only in the narrow case where tools or skills were toggled *within* one thread. Every figure derived from this already renders with a `~`. Against the behaviour it replaces (another conversation's overhead, or nothing at all) it is strictly better.
  - **The cache is gone rather than kept as a fallback.** Its only remaining job would have been serving a pre-migration thread some *other* thread's numbers, which is the contamination being removed.
